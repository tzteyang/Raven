# 真实专家包案例测试方案

当前进度：包含新版 Planning 的三例 DeepSeek 验证已结束，使用正常根子部署；招聘完成两轮交互，旅行与小红书停在生成修复阶段。此前搜索凭据缺项已解决，旧旅行运行的最终状态是执行超时。以下阶段记录保留历史条件，最新结论见 [本轮验证记录](expert-package-validation.md)。

状态：已获准按[说明与真实案例入口对齐计划](curator-docs-and-scenario-alignment-plan.md)实施。日期：2026-09-29。

初稿阶段只做材料阅读与既有证据核对。当前实施正常架构下的案例入口，后续结果以实际记录为准；本方案及此前局部测试不构成五案例全面验收。

输入目录为主工作区的 里的专家包输入目录（不入库）；实现与本方案位于现有策略工作区。后续开测时再记录两个目录的版本和材料快照。遵循 [experimental 开发准则](../AGENTS.md)，承接[四策略代码生成评审](strategy-code-generation-review.md)。

## 1. 要回答的问题

检验这条实际链路：

**真实产品专家材料 → Curator 理解与代码生成 → 四策略负责行为和资源 → Raven adapter 装配 → 原生 Raven Loop 执行 → 专家任务与反馈修订。**

结果分别回答三个问题，不能相互代替：

1. **构建是否成立**：Curator 读到了什么，生成了哪些策略代码，哪些材料成为 Skill、初始上下文或工作流程，哪些能力明确不可用。
2. **运行是否生效**：模型实际收到什么，读到了哪个已安装 Skill，执行了哪个工具，工作状态如何更新，控制请求是否真正实施。
3. **是否形成所需专家行为**：能否应用材料中的方法完成任务，并在约束变化后继续工作，而非仅复述身份或方法名称。

本轮不评判材料的完整行业正确性，不扩成领域知识考试，也不以材料中的增长率、转化率等目标数字作为真实业务成效。材料里需要实时核实的内容仍需证据；缺少数据或服务时，检查限制是否被准确表达。

## 2. 案例及其不同价值

下表路径均相对输入目录。五个包另有隐藏的插件清单 `.<产品>-plugin/plugin.json`，其中的 agents/skills/rules 引用、专家类型和入口关系也属于阅读材料；上一轮仅列显式目录，漏列了这一层。只将头像视为展示资源，不自动转成专家行为；许可证和来源信息随材料留存。

| 案例 | 实际材料形态 | 本轮最有价值的验证 | 范围与条件 |
|---|---|---|---|
| `travel-itinerary-expert` | `agents/travel-itinerary-expert.md`；`skills/travel-planning/SKILL.md`、三个 references 和一个 template | 完整现成 Skill 的代码驱动采用；画像进入初始上下文；需求采集、方案、改线的连续工作 | 首批；涉及实时票价、签证、路况时需真实检索，离线任务只要求方法和待核实项 |
| `recruitment-expert` | 长篇 `agents/recruitment-expert.md`，含流程、评分和交付规范；没有随附 `skills/` | 从规范生成可复用 Skill；把材料拆成画像、方法和当前职位状态 | 首批；使用虚构职位和匿名合成履历片段，只检查岗位能力与证据组织，不作真实录用或法律判断 |
| `xiaohongshu-operations-expert` | 专家画像；`xiaohongshu`、`humanizer`、`marketing-skills` 三个包；marketing 包含 23 个参考模块 | 多 Skill 的发现、选择与协作；按需读取嵌套资料；内容方法与平台执行能力的区别 | 首批；`xiaohongshu` 依赖 MCP，并引用当前目录未提供的若干子 Skill，不能仅凭文档声称已具备这些能力 |
| `growth-hacker` | 画像；`market-researcher`、`marketing-skills`、`ima-skills`；IMA 有子目录和 `.cjs` 脚本 | 大包按需消费；非 Markdown 资产保存；外部知识库操作的依赖处理 | 第二批；先做本地增长方案，IMA 只验证缺凭据/服务时的处理，实际知识库读写另列条件 |
| `deep-research` | `rules/deep_research.md` 是主研究者规范；`agents/deep-research-expert.md` 是子研究者画像；微信搜索 Skill 含 Python 脚本与 API 说明 | 正确识别根/子角色；主流程、委派、资料回传；脚本 Skill 的实际执行 | 第二批；父子 Harness 路径先修复；真实搜索成功与网络受限分别报告，不能将本地回放称作联网成功 |

这些材料沿用原产品的工具名、模板变量、安装说明和元数据，例如 `use_skill`、`Task`、`Read`、`{{.CurrentDate}}`。测试要观察 Curator 如何对齐当前 Raven 的真实能力，不预先替它翻译成策略实现，也不把材料中的“系统级”描述视为可以覆盖宿主权限的授权。

旅行 README 与 agent/Skill 中存在版本细节差异。输入时明确 `agents/`、`rules/` 是行为要求，`skills/` 是对应作业方法，README 用于目录和用途说明；只记录影响本任务的冲突及处理，不开展材料清洗工程。

## 3. 测试方式与最小对照

选择“有限真实任务 + 代码和运行证据”。只验文件安装不能回答是否形成专家；直接跑完整多轮经营模拟又会混入业务素材、用户模拟和外部服务的不确定性。先用固定的小任务验证，再决定是否进入现有 simulation 的长程评估。

| 组别 | 输入与能力 | 用途 |
|---|---|---|
| A：普通 Raven | 相同模型、基础工具和预算，不提供专家材料 | 观察原生模型已有能力，避免把常识回答算成 Curator 的贡献 |
| B：直接提供材料 | 相同原生 Raven；提供画像/规则文本及相同原始文件目录，通过普通文件工具读取；不生成策略、不预安装领域 Skill | 区分材料本身的帮助与 Harness 构建的贡献 |
| C：Curator 构建 | 相同模型与宿主基线；材料先交 Curator，由其生成策略代码和配套资产，再激活候选 | 检验用户要求的架构与专家行为 |

旅行运行 A/B/C；招聘和小红书先运行 A/C。增长、深度研究先做 C 的依赖与运行验证，不强行复制所有对照。每组使用独立工作目录和会话，不能共享另一组的安装结果、记忆或答案。

固定模型为此前指定的 DeepSeek V4.1 Flash 配置。记录配置请求值、实际请求的 model 字段、服务返回的模型标识及采样参数；当前调用路由曾使用 `deepseek/deepseek-flash`，不能仅凭别名宣称锁定了某个模型版本。如果服务不返回足以确认的版本信息，就明确保留这个限制。

各组通过正常员工入口获得同样的根／子基线和基础工具授权。Curator 可选择根层独立完成、使用既有子层或定制部分子层；测试不预先禁用委派、删去插件或把专家固定成单 Worker。各组使用相同任务卡、相同后续事实和相同基础工具授权。测试任务包含的用户约束可以进入 Curator，评估检查点和标准答案不进入生成材料；专家先完成 onboarding，具体任务随后交给 Worker。若生成策略调整采样、上下文或执行预算，记录有效差异，不将结果表述为仅由 Skill 带来的改善。

每组先跑一次，不用多个随机种子刷出通过结果。小样本用于发现行为差异和实现缺口，不支持统计性优越结论。若普通 Raven 已完成任务，如实报告；C 的结构和可维护性价值仍可单独成立。

## 4. 保持 Curator 的生成责任

测试驱动只负责暂存输入、提交目标、启动 Curator、激活候选、发送任务、收集证据和执行版本切换。它不能提前写 profile、安装 Skill、拼出 Playbook，或替 Curator 填入完整策略参考实现。

输入路径按实际场景覆盖，不做“所有专家 × 所有输入形式”的全组合：

| 输入形式 | 所用案例 | 具体边界 |
|---|---|---|
| 现成目录包 | 旅行首次构建；多 Skill 案例 | 完整提供相对目录、frontmatter、references/templates/scripts；由策略决定接纳 |
| 上传材料文档 | 招聘首次构建 | 通过材料入口提供 agent 文档，要求把可重复使用的结构化面试和评分规范整理为受管 Skill；不提供现成 Skill 或 Python 类 |
| 直接消息内容 | 旅行 V2 | 在 Curator 反馈中直接给出一个小 Skill 的名称、正文和引用文件内容，要求采用；所有文本完整提供，不与被截断的目录输入作等价比较 |

招聘这一设置检验“按需求从规范生成 Skill”，不能据此宣称 Curator 在无要求时一定主动选择 Skill。其他任务中合理沿用原生能力或选择别的表达，也应被记录。

文件上传在这里指已经到达 Harness 可访问材料目录的文件交接，不假装覆盖产品上传 UI 或 ZIP 解包。ZIP 不作为本轮阻塞项。普通 Worker 收到消息也不能被默认为触发 Curator；本轮反馈明确送入 Curator，自动触发策略不在此新增。

采用现成包时，核查完整路径集合和文件内容；允许在确有 Raven 适配需要时产生派生版本，但须保留原件、逐项说明转换及消费者。不能把目录压成摘要后称为完整采用，也不能把所有嵌套 `SKILL.md` 都误注册为互不相关的顶层 Skill。

## 5. 首批三个任务

### 5.1 旅行：完整包采用、初始上下文和持续改线

**构建目标**：用专家画像与整个 `travel-planning` 包创建旅行专家，不预指定它必须修改哪几个策略。

最多三轮任务：先给出有部分缺项的北欧冬季家庭出行需求；再补齐儿童年龄、长辈体力、天数、预算和交通偏好；最后缩短天数或降低步行上限。各组获得相同补充事实。首轮考察问题是否集中且不超过材料规定的六个；后续观察是否沿用已知信息。

交付遵循原专家要求，形成完整逐日行程、预算口径、预订时间轴与避坑信息；不把真实多日任务缩成两个代表日来降低难度。预算上限用于控制资源消耗，达到上限应报告受限，不能缩减业务要求后宣布通过。日期、价格、库存等实时事实未核实时只能标待核实；不以编造精确数字换取输出完整。

验收证据：

- 现成包五个文件在受管安装目录中完整存在；策略代码作出采用决定，且能定位对应注册或宿主调用。
- Memory 或保留的原生路径把画像、工作规范和必需上下文送入真实模型输入；没有仅出现在文件中而未被消费的“初始化成功”。
- Worker 自主发现并消费 Skill；在本任务中实际取得冬季参考和行程模板。证据可以是工具读取或有来源记录的模型输入，不强迫固定的工具调用顺序。
- 方案应用人员体力、冬季日照与弹性备选等约束；修改需求后保留其他已知条件，并解释受影响的部分。
- 读取来源是已安装包；从 uploads 回退读取成功不能掩盖安装后权限或相对路径错误。

在任务完成后，仅本案例追加一次 Curator V2：通过消息提供一个短小的 `travel-material-audit` Skill，含正文及一个核对表引用，要求保留原旅行包。检查新代码如何采用它，再启动一个需要核对材料的任务。随后撤去临时输入副本的可见性并重启，检查资源仍可读、既有用户事实仍保留；最后激活保存的 V1 并重启，确认 V2 新增 Skill 下线而原包仍在。

这一回退使用真实版本激活机制，不手工删安装文件；它证明版本回退与资源退出，不冒充 Curator 对自然语言撤回指令的理解测试。

### 5.2 招聘：从长规范生成 Skill 和可复用流程

**构建目标**：提供原始画像文档，并要求将结构化面试和评分规范沉淀为可复用 Skill；其余画像、工作状态如何组织由 Curator 决定。

最多三轮任务：给出一个虚构岗位和业务目标，请形成岗位能力项与结构化面试提纲；补充两段匿名工作经历，要求仅提取与能力项对应的证据、未知项和追问；最后调整岗位侧重点，要求修订问题与评分锚点。任务不要求给真实个人作录用决定或推断受保护属性。

验收证据：

- 新 Skill 来自 Curator 生成的内容及 Capability 的采用逻辑；正文、必要参考和模板均有实际用途，不只是给整篇画像加一个文件名。
- 区分职位要求、证据、尚未证实的信息；评分锚点与具体工作行为对应，不将材料中提到的平台自动当作已连接工具。
- 工作顺序体现需求确认、能力框架、问题设计与证据回收；岗位变化后能修订已有产物而非全部重问。
- 新会话下仍能发现这个可复用 Skill；当前岗位事实是否跨会话保留，按生成实现的显式承诺评价，不默认等同于全局知识。

不以画像中的平台现状、法律条款或示例代码能否直接运行作为本轮标准；这部分只检查有无被错误地宣布为已验证事实或已连接能力。

### 5.3 小红书：多 Skill 协作和执行依赖

**构建目标**：提供画像与三个完整 Skill 包，形成可做内容工作、并能准确表达平台能力边界的专家。

最多三轮任务：给出虚构品牌、受众、已确认产品事实和一段生硬文案，要求定位、三个选题及一篇本地草稿；再收紧语气或受众，要求保留事实后修改；最后提出查看平台同类笔记的请求，观察其按实际 MCP/子 Skill 可用性处理。

验收证据：

- `marketing-skills` 按需消费相关参考模块，`humanizer` 用于文案修改；不把 23 个模块全部塞进 system prompt 才算支持。
- 草稿反映给定受众与品牌事实，修改不虚构体验、热度或平台数据；可以定位实际使用的方法来源。
- 正确区分可在本地完成的写作与需要 xiaohongshu-mcp 的平台操作；若源 Skill 把“内容策划”也路由到缺失组件，记录 Curator 的范围划分，不能默默宣称完整兼容。
- MCP 或引用子 Skill 未提供时，给出当前 Raven 环境的具体缺项，不捏造成功返回，也不承诺这里存在原产品的 `/setup-xhs-mcp` 命令。

本轮没有连接的真实发布/评论通道，不进行平台写操作。能力缺失导致不能执行，只能证明依赖处理；不能记为 Action 的确认拦截已经通过。该强约束需要后续具备隔离执行通道时，单独观察“请求到达、被拦截、获准后执行”的证据。

## 6. 第二批两个任务

### 6.1 增长：大包和脚本资产

提供一份小型、固定口径的虚构漏斗数据，要求识别待验证问题，选一个增长假设，输出实验方案、主指标、保护指标与停止条件。不给真实经营系统写入授权，也不把画像中的成功率当作必须实现的结果。

检查三个包的采用结果，尤其是 marketing 嵌套模块、IMA 的 `notes/`、`knowledge-base/` 与 `.cjs` 文件是否完整保留；记录与任务有关的模块是否被消费。再请求把结论整理成待写入 IMA 的内容，检查凭据、目标对象与服务不可用时的明确反馈。保存脚本不等于执行脚本成功；本轮不据此宣称 IMA 集成完成。

### 6.2 深度研究：根/子职责和脚本执行

选择一个范围明确、非高风险的技术资料比较问题，给定时间范围和输出规模。主规则、子 agent 画像与搜索包一起交给 Curator，让它解释并实现 Raven 下的角色绑定。测试驱动不能直接把子画像当作根 system prompt，也不能提前生成子 Harness。

条件满足时，运行一个范围明确且需要证据汇总的真实研究任务，由 Curator 决定子任务分工；核查其是否落实材料要求的父子委派与回传，并从安装后的 Skill 路径调用搜索脚本、携带规定时间参数。检查主流程是否接收子结果、来源是否来自真实取得的页面、最终结论是否区分证据与推断。

宿主按正常配置提供可用子基线并公开资源预算，Curator 在这些边界内选择流程和分工；不预先将研究流程压成单子任务。网络失败、搜索结果为空、可执行依赖缺失分别记录；不得用伪造搜索响应或预写报告替代。无法联网时，可保留已完成的构建/委派结论，但专家研究任务标为受限，不能报全链成功。

## 7. 四策略与跨策略检查

每个案例都记录下表，但没有业务需要的格子可以“沿用基线”或“不涉及”。四个类、四份文件、固定 helper 数量和固定代码行数都不是验收指标。

| 责任 | 检查内容 | 足以支持结论的证据 |
|---|---|---|
| Memory | 初始消息和画像组成；相关状态保留；反馈后上下文变化 | 生成方法/资产来源、真实 provider 输入及会话状态；只看 profile 文件不够 |
| Capability | 材料转成工具/Skill；接纳、选择、版本和退出 | 策略调用及结果、原生注册表、安装路径、实际资源消费；文件存在不等于可用 |
| Planning | 当前任务状态与流程；确有需要时采用 Playbook/子节点 | 状态变化、原生流程事件或公开交互结果；回答中列步骤不等于执行了计划协议 |
| Action | 材料要求的监控、审查、交互和效果 | 具体事件、决策、实际效果回执；提示词里的“必须确认”不等于宿主拦截 |
| 跨策略 | 生成的 Memory/Planning/Action 交互出口使用 Capability，仍回到正确 owner | 工具调用、接收 owner、相应状态/控制效果；只注册工具名称不够 |

若真实业务要求一个交互出口，而 Curator 选择生成它，就检查完整路径；不为了凑四策略交叉而给每个专家附加无关记事工具。已通过的底层交互测试可以作为机制背景，不能代替真实 Curator 是否会正确选择和生成的证据。

架构必过项：生成出口只接受四个 `*.strategy`；业务资源由生成策略决定采用，资产本身不自动生效；配套 JSON/Markdown 合法，不能绕过 owner。合理继承公共默认方法、覆写受保护方法、调用原生服务都算真实实现，不要求重写底层工具或 Loop。

## 8. 执行次序、预算与停止条件

当前专家入口为 `uv run python -m experimental.simulation.experts`，接收 `--expert`、`--config`、全新 `--output` 及可重复的 `--request-file`。五个源目录均使用此入口，不再使用旧旅行临时脚本。它与 simulation.hire 共用 hire_task，保留正常员工的 generic/可用产品子基线、工具和既有无人值守约束；不额外关闭委派、检索或插件。构建目标只列完整原包与自然要求，任务卡在构建后才发给 Worker。

运行目录保存 `inputs.json` 的完整来源清单、`before.json`/`after.json` 的根和子事实、`generation.json`、实际任务执行与 `result.json`。结果分别列出 available_children、children_requested_for_curation、child_targets 和 observed_child_executions；这些字段不能相互替代。没有 request-file 时仅做构建，task_validation 为 not_run。

本次入口迁移的离线证据：材料与部署、生成契约等 93 项测试通过；原先失败的父子组合路径与部署回退两项定向原生集成通过。它们证明入口及相关机制，不代表真实模型或五案例的业务表现已经通过。原始失败记录保留在第 10 节。

以下步骤在入口对齐后分批执行；入口验证与专家任务表现分别报告：

1. **准备关卡**：固定代码版本、输入副本、基线和模型；修复已知阻断本方案的迁移/驱动问题，只跑与修复直接相关的检查；确认新旧实验记录隔离。
2. **旅行 A/B/C 与 V2**：最短地验证整包、代码生成、原生消费和资源生命周期。架构链路失败时先定位，不立刻复制到其他案例。
3. **招聘 A/C、小红书 A/C**：覆盖生成 Skill 与组合 Skill。两者按各自范围报告，不用对方成功掩盖缺失功能。
4. **增长 C、深度研究 C**：前置能力满足后运行，受外部依赖限制的项目单列，不扩大为全产品/全模型矩阵。
5. **独立复核**：用原始需求、源码和实际记录复核结论，汇总问题归属及最小修复建议，然后结束本轮。

建议上限：首批三次首次构建加旅行一次 V2，第二批再加两次首次构建，共最多六次 Curator 生成任务。每次 `max_calls=24`、`max_queries=24`、`max_checks=2`、`max_repairs=2`；单次模型请求最长 180 秒，整个生成任务最长 15 分钟。达到上限保存进度和原因，不自动加预算继续。

首批对照合计七条对话，每条最多三轮；每轮模型调用上限六次。旅行 V2/重启/回退另用最多三次简短交互，招聘复用另用一次新会话交互；第二批每例最多两轮，深度研究的子调用按实际计划单独累计；若预算不足，应报告未完成范围，不能用固定一名子研究者替代所需分工。限制是资源上限，不是要求模型把次数用完。生成阶段探查引发的 Worker 调用也要记入总量，不能只报顶层 Curator 次数。

记录实际调用数、tokens、时长和服务错误；没有可靠单价时不估报费用。结果明确即停止，不因分数不理想重复抽样。一次明确基础设施故障可以在修复后恢复原任务，保留失败记录，不增加新案例。

## 9. 判定与交付证据

每个案例分别给出“构建”“原生生效”“专家任务”三项结论：通过、部分通过、失败、受限或未执行，并逐项附证据。不把它们加权成一个总分，也不使用姓名、关键词或模板标题命中代替语义验收。

专家任务只评本节任务中列出的可观察点：需求理解、方法应用、约束保持、修改连续性和证据诚实。先人工/独立审查原始轨迹；默认不另起一套 LLM 裁判来评价 LLM 自述。C 优于 A/B 是待观察结果，不能写成预设通过条件。

每次运行最少保存：

- 输入来源、文件清单与摘要、给 Curator 的原始需求、代码版本和宿主基线；凭据不进入报告。
- Curator 的读取/检查记录、生成轨迹、最终四策略 bindings、完整生成源码、配套资产与 V1/V2 差异。
- 安装后的资源清单、来源与派生关系、真实注册/权限状态、provider 实际输入、工具结果和原生事件。
- 对话与产物、模型请求/返回标识、有效采样参数、调用用量；每个结论对应的证据位置。
- 失败分类：输入未传达、阅读路径不足、生成协议使用错误、adapter/原生消费失败、模型行为不稳定、外部依赖或测试驱动问题。不能将它们都称作“Curator 不够聪明”。

运行产物保存在仓库外的独立目录，仓库只落计划和必要的小型可复现测试；不提交头像、长日志或生成报告资产。后续若要融入 simulation，优先复用 Curator/Worker/Recorder 等入口。当前这些专家包没有 `Scenario.load()` 所需的 `profile.md`、`personas/`、`scenario.json` 结构，不能声称现有 suite 已可直接运行它们；先做小驱动，不重写 simulation。

## 11. 材料到四策略的静态覆盖审查

本节保留入口调整前的静态审查；当时没有执行新的生成或测试。结论是：四策略能够承接主要业务语义，但不能宣称五个包已经完整转换；其中有格式解释缺口和子角色装配边界。下面的归属是可行表达，只有旧旅行 V1 部分另有生成源码证据。后续入口调整结果见第 12 节。

### 11.1 材料按语义分解，不按文件类型机械归类

四个一等生成入口是策略实现。Skill、模板、画像和 Playbook 仍有实体，但采用与行为由策略代码决定。一个 `agents/*.md` 可以同时包含画像、流程和约束；一个 Skill 的正文也可以同时影响上下文、工具选择和执行判断。

| 案例 | Memory 的表达 | Capability 的表达 | Planning 的表达 | Action 的表达 |
|---|---|---|---|---|
| 旅行 | MoLA 画像、语言及输出风格；旅客事实与偏好；按当前调用组织 Skill、模板和需求 | 采用完整 travel-planning 包；选择并交付相关正文；保留读文件与需要的检索工具 | 需求采集、骨架、细化、报价、修改的当前进度；需求变化后修订计划 | 若承诺宿主控制，检查报价/实时信息的证据、不代订等行为边界；不把提示词条款直接当作已实施的 gate |
| 招聘 | 专家画像；当前职位与已有事实；将长规范中相关部分放入当前上下文 | 按复用需要生成面试方法、评分模板或 SOP Skill；已有 ATS/招聘平台连接的发现与选择 | 需求确认、问题设计、证据回收、后续安排的状态；保存待补信息与改动 | 检查输出是否越过证据，实际外部操作是否满足材料声明的前置条件；不靠画像文字声称已有外部系统能力 |
| 小红书 | 品牌、受众、语气及内容事实；保留修改上下文 | 三个包的完整采用；营销模块与 humanizer 的相关性选择；连接真实 MCP 能力 | 定位、选题、草稿、修改、待确认、发布与复盘的流程状态 | 平台工具调用前的可用性/登录判断；发布和评论的确认约束；结果 ID 的真实来源 |
| 增长 | 产品背景、指标口径、已知数据与历史实验结论 | market-researcher/marketing-skills/ima-skills；完整子目录与脚本；Node、凭据、工具可用性 | 增长假设、实验设计、执行状态与复盘；知识库读取/写入的依赖顺序 | 预算或停止条件在实际执行点的判断；IMA 目标与参数检查、失败处理；不把建议当执行结果 |
| 深度研究 | 主规则与子画像分别进入对应 owner；日期、产物路径和来源证据使用当前宿主值 | 微信搜索包、脚本及检索工具；发现已有可委派的子 Harness 能力 | 查询分类、研究计划、子任务依赖与回传；静态部分可用 Playbook，运行中进度由 initialize/interact 与已提交计划投影 负责 | 调用预算、时间筛选、失败与结果证据检查；只在实际可观察的阶段承诺控制 |

角色有表达入口，不表示每个案例必须生成四个类。沿用满足需求的原生机制是合法结果，但需要说明实际消费者。把流程写进 Skill 可以满足模型指导；若同时承诺可恢复进度或不可绕过的约束，则还需要相应状态和执行机制。

例如小红书“发布前确认”：Capability 提供真实发布工具，Planning 可以维护待发布草稿的状态，Memory 组织草稿和用户确认上下文，Action 在调用前判断确认是否对应这次操作。它们共同使用同一事实与状态所有者，不各建一份独立审批状态。

### 11.2 旅行 V1 实际生成了什么

已有产物只有 `memory.strategy` 与 `capability.strategy`。源码与原运行驱动可确认：

- 输入包含 README、agent 画像和完整 travel-planning 包；并非只提供了 README。原驱动没有交付专家包根部的插件清单。
- `TravelCapability._prepare_skills` 返回携带实际 root/digest 的 SkillContribution；继承的 prepare 经 register 接纳整包。select 委托原生选择。
- `TravelMemory.initialize` 保存初始化信息；compose 将代码中的画像、作业规则作为 system 消息加入每次模型输入，并保留原有消息。这份实现没有通过 host.profile 生成画像文件，但仍是代码拥有上下文表达。
- 流程顺序与行为条款主要进入 Memory 中的文本及原 Skill；没有生成专门的 Planning 状态机或 Action 执行检查。不能据此认定运行时一定遗漏，也不能声称已具备显式流程状态或强约束。
- 原任务明确关闭网络访问，因此生成代码将实时核实要求降为“不能核实时标明”。这是当时有意限定范围后的表达，不能视为原专家实时能力的完整还原。
- 驱动导出失败后，没有完成真实专家任务及 V2 验证。源码能证明生成形式，不能代替模型实际遵循的证据。

其余四例没有新的生成产物。本节不把建议归属描述成已生成事实。

### 11.3 已确认的缺口和有限支持

| 项目 | 当前源码或材料事实 | 对转换完备性的影响 |
|---|---|---|
| 专家包入口信息 | [inspection/runtime.py](../curator/raven_adapter/inspection/runtime.py) 可以把已暂存的文本作为通用 upload source；没有专家包关系的专门解释。前次旅行驱动只交付选定文件 | 通用读取能力存在，但遗漏暂存的 manifest 不会自动补回；需要读入 agents/skills/rules 的关系。图标、标签、快捷提问不必强制变成策略 |
| Skill frontmatter | [registry.py](../../raven/memory_engine/skill_local/registry.py) 的 `_parse_frontmatter` 按行拆 key/value；`_parse_nested_metadata` 只解释 metadata 内的 JSON 字符串 | IMA、小红书的 `description: |` 不会得到完整描述；IMA 的嵌套 YAML `metadata.openclaw.requires.env` 不会进入 Raven requires。文件复制完整仍可能丢失发现描述与依赖语义 |
| 工具限制元数据 | humanizer 的 `allowed-tools` 是 YAML 列表，使用 Read/Write/Edit/Grep/Glob/AskUserQuestion 名称；当前这条链没有消费该列表的约束逻辑 | 若要承诺保留工具限制，需明确 Raven 名称、作用域及权限/Action 的实际执行点。工具依赖 `requires.tools` 和执行许可不是同一种含义，不能互相冒充 |
| 嵌套 Skill 的输入关系 | [materials.py](../curator/raven_adapter/materials.py) 对每个 SKILL.md 独立列包；原生 registry 则会跳过已识别 Skill 下的嵌套 SKILL.md | marketing 的参考模块和 IMA 的子模块会同时出现在输入候选清单，缺少显式父包关系。整包安装有保留嵌套内容的实现，但输入仍可能引导重复采用或错误拆包；这是歧义，不是已证实的安装丢失 |
| 小红书外部依赖 | 原包引用 setup-xhs-mcp、xhs-login、post-to-xhs 等子 Skill，但当前目录只有一个路由 Skill；MCP 连接不是正文的一部分 | 文件采用不能补齐真实平台能力。CapabilityHost.mcp 有连接入口，仍须具备实际连接配置；缺失子 Skill 需要明确补充、实现替代或报告不支持 |
| 脚本能力 | [capability/catalog.py](../curator/raven_adapter/capability/catalog.py) 保留包文件及执行位，Skill 渲染提供实际目录；接纳阶段不执行脚本 | IMA 的 Node/凭据与微信搜索的 Python/网络仍需运行时条件。相对 shell 路径、原产品工具名及模板变量不做通用自动翻译；可通过生成代码适配，不能把保存成功算作执行成功 |
| 深度研究子角色 | [hosting/prepare.py](../curator/raven_adapter/hosting/prepare.py) 只解析 generic 或支持的已部署 Raven 产品子基线；CapabilityContribution 当前只含 tool/skill | 可以将研究者语义落到既有子基线的策略中；不能直接把任意 agent.md 注册成新的具名子 Harness。若要求保留任意原角色身份和自动接纳，还缺明确的接纳契约；组合路径另有已知字段迁移错误 |
| 全部需求覆盖 | [Plan](../curator/harness/artifact.py) 描述选中 target 的设计、状态和验证；设计提示要求连接触发与消费者，但没有逐条源要求的处置记录 | 可以生成合法、可装配的候选，同时遗漏未被选中的要求。当前检查没有提供“原包语义已完整转换”的保证 |

上述 frontmatter 结论来自静态代码推导，不是这次运行了 IMA 或小红书后得到的实测。它是现有原生解析限制，在本轮复用完整包时暴露出来，不是四 Target 收敛本身导致的字节丢失。

### 11.4 对后续方案的修正

在原准备关卡加入专家 manifest/包关系盘点、实际 frontmatter 解释核对及深度研究子基线绑定确认。它们先于相关案例的“完整采用”结论；本次入口调整不自动意味着解析器和外部能力接纳缺口已修复。

建议复用现有 Plan 的 design/verification 或附带审查记录，记录关键要求的去向：**源要求 → owner 与实现位置 → 保留的原生消费者 → 已支持/待实现/受限/不涉及 → 验证证据**。这是生成覆盖性说明，不是新增业务生效入口；尚无必要仅为记录它就增加第五策略或恢复旧 targets。

优先处理会让模型看不见或误判能力的通用问题：材料关系、元数据解析、外部依赖与子角色装配。然后验证 Curator 是否合理将行为分配给四策略。展示字段、相同内容的非必要重复以及不影响所选任务的行业条目不作为强行改造理由。

使用完整旅行包、正常员工准备和此前 DeepSeek 配置尝试一次真实运行。该配置未禁用工具或插件；运行在准备 Raven-Research 子基线时因缺少 Serper 搜索凭据停止，尚未进入 Curator 生成或客户任务执行。原错误、完整材料清单和状态保存在 当时的临时目录（未入库）。没有通过关闭 Research、删去检索或注入模拟响应使它通过。

这证明新入口实际使用正常子基线准备链，也暴露了当前运行环境的依赖缺项；不能据此断言 Curator 已选择根层完成或两层分工。补齐真实配置后，使用新的输出目录重新运行同一入口，再按本方案记录 Curator 选择与实际执行。其余四例目前只确认材料入口可识别，未做新模型评估。

后续联合验收已补齐活动测试中的旧接口示例，以及上传断言仍期待改名材料的问题。入口现在先保存 configured_subagents，准备后报告 prepared_children，逐个原生进程检查成功后才记录 available_children；准备失败不再只剩一条错误而丢失原配置线索。真实生成和客户任务仍等待 Research 搜索配置，当前证据及可复用运行材料见[联合验收表](curator-docs-and-scenario-alignment-plan.md#7-与-action-实现的联合验收)。
