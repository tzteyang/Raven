# 增量策展与语义判断：实施计划

状态：v2 已实现，未提交。计划评审见第 12 节；实现评审与处置见 13.3；离线转写与 DeepSeek 流程验证见 13.2 与 13.4（只有“一个决定内多次推断”这一项还没验证到）。日期：2026-10-09。范围：`experimental/harness/curator/` 的生成流程、安装与策略推断宿主；评价分支、`raven/`、模拟场景与材料不在本计划内修改。

## 1. 要解决的问题

10-07～10-08 的品牌策划案例（cmp-a1/a2/b1/b2、gtm-sol-2、gtm-11、gtm-iso-2 等运行）暴露出三组问题。按主线（Curator 生成的 harness 是否满足材料约束、改进不足、保留已做对的部分）排列。

**(1) 改进不是有机制保证的增量。**

- 代码层面：候选必须基于当前安装版本，未选中目标的绑定原样保留；但文件不受目标边界保护（一个只选了 planning 的候选也能改 action 引用的模块），选中目标的文件只能整份重写（`stage_file`）。gtm-sol-2 第 1 轮的 capability 文件只留下 25% 的旧行，逐段比对发现大部分是格式噪声（引号、换行、删掉 docstring 和四条记录隐藏约束的注释），真正的语义改动混在里面：给模型的指导文字里删掉了一条旧规则，又新加了几条，记录里没有任何地方写明。
- 语义层面：每次策展的计划（`Plan.understanding/design/changes`）是整篇散文；下一次策展只把它当作上一版的设计（`previous_plan`，`materials.md` 材料表）来读，没有一份持续存在、可逐条增改的“harness 现在承担哪些行为”的表达。cmp-a2 第 1 轮的计划同时写了“保留已成功的委派与交付”和“核对做不成就结束本轮”，两句埋在 10 KB 设计文本里，没有任何环节指出后者会拦住前者；第 2 轮交付全部被拒。
- 行为层面：安装前检查只验证候选能构造、探针不报错（`worker.check` + `probe.exercise_translations`），不比较新旧版本的决策。

**(2) Curator 生成的语义护栏大多跑不成。**

策略推断（`infer`）是规则落到语义层面的唯一手段。实际记录：

| 运行 | 单次输入 | 输出上限 | 成功/总数 |
|---|---|---|---|
| cmp-a1 | 31–41 KB | 2048 | 3/22 |
| gtm-sol-2 | 32–36 KB | 2048 | 3/25 |
| cmp-b1 | 13–20 KB | 8192 | 10/16 |
| gtm-11 | 约 3 KB | 2048 | 35/61 |

原因叠在一起：生成的策略一次判断审全部规则和全部原文；推理 token 从输出上限里扣（当时宿主写死 2048 或 8192）；宿主规则“每个策略操作只能推断一次、失败不能重试、每轮最多 4 次”；判断做不成时一律拦或一律放。离线实验（DeepSeek Flash，即 worker 自己的模型）显示：一条规则对一条消息的小判断，36 次里有 34 次能给出结果；规则写明边界后，该拦的和该放的各对了 8/9。而现行宿主规则不允许把同一个决定拆成多次判断。

**(3) 宿主限额在 9-29 定下时没有用真实案例校准**（见 `semantic-intervention-plan.md`，当时只做了两次小的真实模型判断）。当前检出里已经改了两项：输出上限改为“由策略选择，默认取 worker 自己的生成设置”，单次超时由 90 秒放宽到 180 秒。其余限额没动。

**(4) 一个现有的正确性缺陷。** 安装时如果候选没有任何代码变化，`deployment.activate` 会提前返回，不更新 `last_plan / last_attribution / last_selection / last_children`（`raven_adapter/deployment.py` 提前返回分支）。会话随后把 `worker.last_plan` 记为本轮的修订（`iteration/session.py` 的 `_close`），下一轮又把它当作 `previous_plan`。结果是一次没有改代码的策展，会把上一轮的计划、诊断和依据记成本轮的。空选择的子 harness 或普通 worker 走的就是这条路径。

## 2. 目标与非目标

目标：

1. **中间语义层。** Curator 把任务层需求理解成一份持续存在的 harness 承诺条目列表，逐条增、改、撤；代码按条目实现；宿主检查条目与代码改动在目标层面一致。
2. **代码改动可以按片段编辑**，不必整份重写；对已安装文件的改动量，以及对未选中目标所引用文件的改动，在检查结果和记录里可见。
3. **策略推断能把一个决定拆成多次小判断**（顺序调用或宿主并发），限额按用途重设，并保证判断不比 worker 本身更强。
4. **参考资料和提示词说明**：按规则拆判断、写明规则边界；判断做不成时如何处理写进对应条目，并顾及它可能拦住的其它条目。
5. **修复第 1 节 (4) 的缺陷。**

非目标（理由见第 8 节）：回放式回归检查、按目标部分安装、评价侧改造、`raven/` 子任务回报指令、最后一轮归因、资料快照按规则拆单元。

## 3. 承诺条目（Commitment）

### 3.1 概念

三层链：

1. 任务层输入：Analyst 的需求编号、交来的材料、审过的资料快照、路由来的节点需求、任务本身。
2. 承诺条目：Curator 理解后写给自己的 harness 层需求。
3. 四个策略面的代码。

一条承诺条目说的是：某一个策略面，在什么情形下，依据什么输入，做什么，产生什么效果；需要模型判断时，判断做不成怎么办。

- 每条只属于一个策略面，可以服务多个任务层输入；一个任务层输入也可以由多条条目共同承担。
- 宿主原生行为承担、且被已写代码依赖或可能被拦住的输入，可以写成 `surface = "native"` 的条目，没有代码。

术语选 commitment，不用 requirement：仓库里 requirement 已有两种含义（Analyst 的行为需求 R1…、playbook 的节点需求）。条目 ID 用 H1、H2…，也是为了和 R 编号区分。仿真场景的对话里也出现过业务意义上的 commitment（如“不作承诺”），所以 `CONTEXT.md` 给出 _Avoid_ 说明，提示词里一律写 Harness commitment。

### 3.2 锚点选择（三种方案）

条目与任务需求、策略面都是多对多关系，比较过三种组织方式：

| 方案 | 结构 | 结论 |
|---|---|---|
| 需求为锚 | 每条任务需求下列各策略面怎么承担 | 共享机制（例：一个门禁服务 R1–R5，它的失败策略）要写多遍，改一处得改多处 |
| 策略为锚 | 每个策略面下列它服务的需求 | 同一需求跨面的配合看不出来；职责挪面（例：规则从 capability 指导挪到 action 审查）只表现为一删一增 |
| 条目为锚（采用） | 每条只属一个面，`serves` 指向若干输入 | 机制写一次；按需求或按策略面看，都由列表的 `serves` 与 `surface` 直接归组，宿主据此算出 `unserved`（3.7） |

成立前提：机制与需求普遍是多对多（上面两例都是）。两种情况会推翻这个选择：

- 实际条目几乎都是一对一，那么需求为锚更直观；
- 很多逻辑必须几个面紧密配合、拆到单面说不清，说明粒度规则不对。

这两点在验收的离线转写中检查。

### 3.3 存放位置（三种方案）

| 方案 | 优点 | 问题 |
|---|---|---|
| 进程内字段，与 `last_plan` 并列（采用） | 与现有状态模型一致：会话续跑只在同一进程内进行，`last_plan` 本来就这样持有；记录里写一份完整列表供核查 | 进程重启后丢失；现有流程本来也不支持跨进程续跑 |
| worker 目录里的文件 | 重启后仍在 | 引入第二种持久化方式，而现有续跑并不需要 |
| 放进 Artifact | 与代码同版本、计入修订指纹 | 只改条目而不改代码也会触发重新激活；需要扩展 `extend_artifact` 的合并语义 |

### 3.4 数据结构

`experimental/harness/contract/commitments.py`：

```python
class Commitment(BaseModel):
    id: str                 # H<n>，宿主分配，永不复用
    surface: str            # 一个已授予的目标名（如 action.strategy），或 "native"
    statement: str          # Curator 的表述
    serves: tuple[str, ...] # 任务层输入，与归因的 about 同一词汇：需求 id、material:<name>、
                            # information:<version>、node:<playbook>/<node>#<n>、task
    retired: str = ""       # 撤销理由；非空即已撤销，条目保留以免 ID 复用

class CommitmentChange(BaseModel):
    action: Literal["add", "modify", "retire"]
    id: str = ""            # modify/retire 必填；add 由宿主在设计提交时填入
    surface: str = ""       # add 必填；modify 时非空表示换面
    statement: str = ""     # add 必填；modify 时非空表示改写
    serves: tuple[str, ...] = ()  # add 必填；modify 时非空表示替换
    reason: str = ""        # modify/retire 必填；只带 reason 的 modify 表示“承诺不变、实现修订”
```

- `Plan` 新增 `commitments: tuple[CommitmentChange, ...] = ()`，受众为只进记录（RECORD_ONLY）。现行列表是唯一权威来源；上一版计划里的操作不再随 `previous_plan` 重复出现。当前策展自己的计划在实现和修复阶段以原样（不经投影）提供，不受影响。
- `apply(current, changes)` 是纯函数：按顺序应用；add 的 ID 必须是下一个未用编号。
- 不新增“条目的验证案例”字段。验证仍写在 `Change.verification`（只进记录，保持现有的预测准确度测量）；回放案例留到下一阶段（第 8 节）。

### 3.5 宿主检查

**设计提交时（`design.parse`）：**

1. **操作合法。**
   - modify/retire 指向存在且未撤销的 ID；同一 ID 在一次提交中只出现一次。
   - add 带齐 surface、statement、serves；modify/retire 带 reason；retire 不带其它字段。
2. **`surface` 合法**：是当前声明里的目标名，或 `native`。
3. **`serves` 合法**：每项是本次归因诊断过的输入，或已被现行条目引用过的输入。
4. **改动范围。** 下列操作所在的策略面必须在本次选中目标之内：
   - add；
   - retire；
   - 改写 statement 或换面的 modify（包括原面和新面）；
   - 只带 reason 的 modify。

   例外：只改 `serves` 的 modify 和 `native` 面不需要选中，因为它们不要求改代码。反过来，每个选中目标至少有一条条目操作（只改 `serves` 的 modify 在这里也算）；只有当前在该面上没有任何现行条目时可以没有（代码不经设计阶段装入，生产路径里不会出现，只见于直接安装的测试）。这样的代码要保留，就得补上条目，否则实现期检查只允许把它撤掉。
5. **依据一致**：`Selection.grounds[X]` 里的每个输入，必须被应用本次操作后 X 面上的某条现行条目服务。
6. **分配 ID**：宿主为 add 填入 ID，返回的计划带着 ID，实现和修复阶段可以引用。

**实现提交和预检时（`implement.parse`）**，对每个选中目标 X，按应用后的列表检查：

- X 有值，则 X 面上至少有一条现行条目；
- X 被 `remove`，则 X 面上不能再有现行条目。

**不做的硬检查**：“每个诊断过的输入都必须有条目承担”。它只作为信息展示（第 3.7 节的 `unserved`），不拦提交。硬拦会让首次策展必须为每份材料写条目，增加失败面而不提高正确性。

**与现有映射的关系**：`Selection.grounds`（目标到输入）在选面时给出，第 5 条把它和条目的 `serves` 对齐。`Change.treatment`（修改、替换、新增）描述的是代码机制相对于诊断出的机制怎么变，是另一个维度；`iteration/history.py` 和 `ledger` 按它分组，所以保留。这是有意保留的重叠，理由已写在这里；如果后续发现 `treatment` 可以从条目操作推出，再合并。

### 3.6 存放与生命周期

- `Worker.commitments` 与 `Child.commitments` 各持一份。`Child` 的那份随 `Child.export/restore` 往返，因此也进入根 harness 的组合事实（按子 harness 名分开，ID 在各自作用域内编号）。
- 生成上下文通过 `collect(..., commitments=...)` 传入。`GenerationState.identity` 和归因的 `input_key` 都纳入现行列表：列表变了，暂停的生成与归因不能续跑。上线前暂停的生成也因此不能续跑，需要丢弃（`resume=False`）。
- **安装（`deployment.activate`）**：
  - 根：`apply(当前列表, candidate.plan.commitments)`；
  - 子 harness：同理，恢复为原始版本时把条目全部撤销（理由写明恢复），编号不复用；
  - 没有代码变化的提前返回分支也要应用条目操作，并同时更新 `last_*`（修复第 1 节 (4)）。条目和 `last_*` 都更新在实际的 `worker` 与 `worker.children` 对象上，不能更新在提前返回时被丢弃的副本上。
- 策展记录（`curation/<uuid>.json`）写入安装后的完整列表。
- 空选择的非根作用域（`generation/run.py` 的快捷路径）不进入设计阶段，也就没有条目操作，列表原样保留。只想补录 `native` 条目而不改代码，只能在有设计阶段的策展里做。这是有意接受的限制。

### 3.7 Curator 看到什么

- **共享材料**新增 `commitments`：现行条目（id、surface、statement、serves）。归因与各阶段都能看到；归因据此在 `mechanism` 里写条目 ID。
- **选面和设计阶段的数据**新增 `unserved` 与 `stale_serves`，二者都在归因完成后计算，不进入归因自己的视图：
  - `unserved`：本次诊断过、但没有任何现行条目服务的输入；
  - `stale_serves`：现行条目引用的 `information:` 或 `node:` 键里，不在本次输入中的那些。这两类键随版本或路由变化；需求编号则长期有效，不算过期。
- **实现与修复阶段的数据**新增 `commitments_after`：应用本次计划后的现行条目。每个选中策略面的代码要继续实现该面上的全部现行条目，而不只是本次改动的条目。
- **提示词**：
  - `design.md`：说明如何提交条目操作和写 statement；
  - `materials.md`：说明现行条目是“harness 现在做什么”的持续表达，`previous_plan` 的设计文本是上一版的历史；
  - `implement.md`：说明 `commitments_after` 和 `edit_file`；
  - `diagnose.md`：说明 `mechanism` 可以写条目 ID；
  - `select.md`：说明选目标就是选“要改哪些面上的条目”。

## 4. 代码改动的表达

### 4.1 方案比较

| 方案 | 说明 | 结论 |
|---|---|---|
| 锚定替换（采用） | `edit_file {path, old, new}`，`old` 必须唯一出现 | 模型熟悉；失败时能精确报错重试；宿主据此得到完整文件 |
| unified diff | 带行号的补丁 | 模型写行号容易错，补丁偏一行就整段作废 |
| 维持整份文件，宿主出差异报告 | 不加工具，只报改动量 | 不能减少重写噪声，只能事后看到 |

采用锚定替换，同时保留整份写入（新文件和确实需要整体重写的文件），并加上差异报告：改动量与“改了未选中目标引用的文件”都要看得见（4.3）。

### 4.2 `edit_file`

- 在实现与修复阶段提供，和 `stage_file` 一样进入共享工具列表，按阶段开放。
- 编辑的底稿按以下顺序选取：
  1. 已暂存的同名文件；
  2. 修复阶段里上一个候选直接提交的文件（`state.candidate.artifact.files`）；
  3. 当前已安装文件（`facts.authored.files`）；
  4. 都没有则报错，提示新文件用 `stage_file`。
- `old` 必须恰好出现一次，否则报错并给出出现次数。替换后的完整内容进入暂存区，与 `stage_file` 的结果一样参与预检和提交。
- 提交的 `files` 里如果出现用 `edit_file` 编辑过的路径，拒收，避免编辑被直接提交的内容悄悄覆盖。现有“直接提交的文件覆盖 `stage_file` 暂存的同名文件”的规则不变。
- 设计重开时暂存区清空（现状不变），之后的编辑重新以已安装文件为底稿。
- 进入修复阶段时，暂存区里的文件改成刚被校验的候选里的版本（直接提交覆盖了暂存的同名文件时，以直接提交的为准），已编辑记录清空：校验前的编辑已经包含在这个候选里，修复时整份重交这些文件是允许的。

### 4.3 差异报告

预检结果、最终验证事件和策展记录中，对候选里每个已安装过的文件给出：

- 保留、删除、新增的行数；
- 是否有未选中的目标直接引用它（按 values 里 `module:attribute` 的模块名，与 `implement.missing_modules` 同一解析）。

整份重写不拦，但会以数字的形式出现在 Curator 下一步的输入和记录里。这一层仍是“可见”，不是“保证”；行为层面的保证要靠第 8 节的回放检查。

## 5. 策略推断宿主规则

### 5.1 保留、修改、去掉

| 规则 | 处置 | 理由 |
|---|---|---|
| 单步、有类型、无工具、无子流程；只在活动 turn 内；结果是数据不是许可 | 保留 | 界定推断是一次判断而不是另一个 agent |
| 只能在操作自己的任务里调用 | 保留 | 并发由宿主原语负责（5.3），策略代码自建的任务仍被拒，不会比操作活得更久 |
| 每个策略操作只能推断 1 次 | 改为每个操作最多 12 次 | 一个决定要能拆成按规则的小判断 |
| 每轮最多 4 次（失败也计） | 改为每轮最多 48 次（失败也计，调用确实发生过） | 小判断数量多；一轮多个外发动作都要留余量 |
| — | 新增：每轮输入合计不超过 512 KB | 次数相同时，大输入与小输入成本差很多；这是在调用前就能确定的成本上界 |
| — | 新增：每个操作的推断时间窗 360 秒（从第一次调用起） | 防止连续多次调用把整轮拖到 worker 超时被杀；窗口内剩余时间作为单次超时的上限 |
| 不重试 | 保留宿主不重试；策略可在额度内自己再调 | 不引入隐藏的重试循环 |
| 单次输入不超过 64 KB | 保留 | 让单次判断聚焦 |
| 单次超时 min(180 秒, worker 生成超时) | 保留 | 小判断耗时短 |
| 输出上限、推理强度由策略选择，默认取 worker 设置 | 收紧 | 推理强度不得高于 worker 配置的强度；worker 没配置强度时，策略不能自选。worker 固定了输出上限时，不得超过它。保证判断不比 worker 本身更强 |

### 5.2 校准

在记录里统计每轮的推断需求（实际调用数加上因额度被拒的调用数），各运行的最大值是：

- cmp-a1：4
- cmp-a2：2
- cmp-b1：3
- gtm-sol-2：7
- gtm-11：6

这些都是“一次大判断”写法下的需求。按每个决定拆成 3–8 条规则估算，每轮需求约 20–50 次，因此每轮取 48 次，每个操作取 12 次。

成本上界按 harness 进程计（子 harness 各有自己的推断宿主）：每轮输入不超过 512 KB，输出不超过 48 × 单次输出上限。worker 自己一轮十几次主循环调用，每次都带完整上下文，两者在同一量级。流程验证时报告实际次数与花费；如果 48 次或 512 KB 经常触顶，或成本明显偏高，回到这里调整。

### 5.3 并发方式（三种方案）

| 方案 | 说明 | 结论 |
|---|---|---|
| 放宽任务检查，策略自己 `asyncio.gather` | 改动小 | 策略可以 `create_task` 而不等待；`gather` 遇到第一个异常就抛出，其余调用继续跑，可能在操作结束、预算释放之后才写记录；需要额外的在途任务追踪与取消 |
| 宿主提供逐条判断并汇总的原语 | 生命周期安全 | 汇总规则（哪些一票否决、未判怎么算）是策略自己的业务，由宿主固定会限制表达 |
| 宿主只负责并发分发的原语（采用） | `infer.each(requests, output_type)` 在当前操作内并发执行，逐项返回结果或 `InferenceError` | 任务归宿主所有，随调用结束而结束，取消会传给所有子调用；一项失败不掩盖其它结果；汇总留在策略里 |

`each` 在开始前一次性检查并预留整批的次数与输入额度，不足则整批拒绝（不部分执行）；每项的记录和单次调用的记录相同。

## 11. 风险与待验证假设

- **Curator 模型不按新格式提交**：设计提交被拒时，错误信息直接说明缺哪条操作；流程验证会暴露这个问题。
- **条目与代码漂移**（条目说一套，代码做另一套）：本阶段靠三点约束：选中面必须有条目操作、实现期检查、实现阶段能看到全量条目。回放检查留到下一阶段。
- **判断次数增多带来的成本**：上界见 5.2，流程验证报告实际数字。
- **口径变化**：改动推断规则后，与 10-08 的运行不是同一口径，对比时要注明。
- **多次判断同一问题再投票**：这在额度内是允许的。它用的仍是 worker 自己的模型，不引入更强的模型，但效果上可能比单次判断稳；这一点交给负责人知悉。
- **待验证**：Curator（DeepSeek 与 sol）能否稳定写出粒度合适的条目操作；并发后一个决定的耗时是否接近单次调用；每轮 48 次是否够用。

1. 两次计划都能表达，宿主检查全部通过。
2. gtm-sol-2 第 1 轮从 capability 指导里删掉的那条旧规则（“内部自检不写成给对方的过程或待办”）表现为 H2 的一次换面 modify：ID 不变，理由写明“指导已供给仍被忽略，改为发送前审查”。
