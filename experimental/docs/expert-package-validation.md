# 四策略 Curator：真实产品案例验证记录

状态：两轮三例均已结束。日期：2026-09-29。第一轮招聘完成两次客户交互，另外两例在生成阶段暂停。第二轮三例均完成生成和安装，招聘、小红书完成两次客户交互，旅行第二次交互因上下文压力衔接错误中断。业务结果与修复证据见第 8 节，不能据进程完成宣称全面通过。

## 验收口径

以最终 Harness 配合指定模型完成实际任务的结果为准：交付是否满足用户需求、事实与约束是否保持、需求变化后能否正确调整，以及失败是否明确处理。生成了几个策略、是否改写全部四面、是否调用子 Harness、某个方法调用了多少次，都不作为通过条件或得分项。

策略选择、资源使用和调用记录用于解释结果、定位代码或机制问题。只有实际任务问题能关联到某个机制缺口时，才判断是否需要改变对应策略；沿用原生能力或仅修改部分策略是正常方案。可恢复工具错误作为效率与诊断事实记录，不自动判定整个任务失败。

## 1. 条件与真实性

使用原始专家包，源目录保持不变。经 simulation.experts -> hire_task -> workflow.improve 进入正常部署，不预安装业务 Skill、不注入策略实现、不关闭正常子能力来简化测试。

模型沿用用户确认的配置，provider 标识为 deepseek/deepseek-flash。根、Curator 与受管理子基线按该配置指定模型。私有配置与搜索凭据只供运行使用，仓库与本文不保存密钥。

窗口条件更正：DeepSeek-V4.1-Flash 官方支持 1M 上下文，Raven 模型表解析为 1,048,576。但本次两轮使用的测试配置显式设置 contextWindowTokens=131072，根与子部署均继承了这个 128K 上限。旅行故障的 87,601 是扣除回复和工具定义预算后的输入额度，不能解释为模型只支持约 88K，也不能把本次执行当作 1M 条件下的验证。后续正常容量验证应取消这一显式覆盖，遵循原生模型窗口解析；受限窗口压测应单独标明。宿主 inspection 及案例 before/after 快照现记录 configured_tokens 与 effective_tokens，避免仅记录模型名而遗漏实际窗口。

每例独立 home、工作目录、检查点和输出目录。三例的 Raven、Raven-PPT、Raven-Research 均通过实际进程检查。Curator 自行决定分工和定制，客户任务在构建完成后才输入。三例均选择 Memory、Planning、Capability，未选择改写 Action。

组合生成的总预算为 32 次模型调用、36 次查询、3 次预检、2 次修复；生成阶段 1200 秒，每条客户请求 900 秒。每例安排首次任务和一次需求变更。未追加模型预算或人工替换生成代码。

源包校验：旅行 10 个文件、招聘 7 个文件、小红书 35 个文件；运行结束后仍与暂存时记录的源文件摘要一致。

## 3. 重复暴露的生成问题

### prepare 签名与方法约束

旅行、招聘都先因 Planning.prepare 的同步签名/注解不满足契约被拒绝，随后通过预检反馈修正。招聘、小红书还出现过 Capability 注册方法的 contribution 参数注解读取错误。说明模型会读到协议，但实际实现仍需要运行检查；错误信息和工厂依赖说明还有改进空间。

### 子 Harness 与流程节点混淆

三例都曾把 Raven、Raven-PPT、Raven-Research 当作 Plan.node_reasons 的键。该字段实际要求当前、新增及撤回的 Playbook 节点标识。

- 旅行准备了 itinerary-customization 流程，正确键包括 intake、verify、design、review 的完整路径。
- 招聘和小红书没有准备 Playbook，正确的 node_reasons 是空映射；子能力分工说明应写进 design。

宿主准确拒绝了这些方案，但修改这个方案字段需要重新进入设计/实现流程，额外消耗调用预算，并出现重新生成代码后的新问题。不能把这一开销仅归为业务材料过多。

## 4. 两个未完成案例的最终失败

### 旅行：投影子类型被严格判等拒绝

最终验证错误为 planning initialization and interactions must use the same projection type。

生成代码使用了不增加字段的 ItineraryProjection(PlanningProjection[ItineraryView])，以及 ItineraryResult(PlanningResult[ItineraryView, TravelReply])。初始化返回前者；结果模型中的 projection 字段继承公共基类类型。

离线最小复核确认：两者的 ViewT 相同，投影子类可以构造合法的结果模型，但当前宿主使用具体类身份的一致性检查而拒绝它。这暴露了宿主类型约束可能过严的问题，不能全部归咎于模型生成无效业务逻辑。原始运行保留失败状态；后续适配器修复见第 7 节，不将原始记录改记为通过。

### 小红书：工厂声明了 Planning 不提供的依赖

最终验证错误为 plan requires a host-supplied keyword-only dependency。

重新生成的 Planning 工厂声明了 host、infer、peers、plan 等参数；该轮 Planning 绑定尚未提供 plan。此前已通过构造预检的版本在重设计后发生了这个变化。需要明确角色工厂依赖与当前已提交视图的读取方式，避免机械复制其他策略的依赖列表。

## 5. 招聘案例具体证明了什么

### 生成内容与 Skill 使用

最终 authored package 包含三份策略源码，以及从原画像资料生成的 recruitment-methods Skill：SKILL.md、4 份参考文档、4 个模板、1 个漏斗分析脚本。该 Skill 被安装到实际 curator-capability 目录。

首轮业务执行实际读取了渠道、筛选/面试、分析、合规参考以及 JD、评分卡模板，执行了生成的分析脚本。因此这里不仅是资源声明或目录存在，有真实读取和使用记录。

原包没有现成 Skill，这一案例验证了 Curator 把资料组织成 Skill，再通过 Capability 代码采用的路径。旅行与小红书的现成包采用只到候选检查阶段，不能作为最终部署后的使用通过证据。

### 运行期四策略行为

- Memory 在两轮都实际 compose，并分别进行了 10 次、4 次信息交互。
- Capability 在两轮分别进行了 12 次、11 次选择。
- Planning 首轮初始化并持续提供指导；一次 Agent 请求错误地使用了 record_criteria 命令，未进入有效规划交互。第二轮成功执行了一次 add_note 交互。
- 本例没有生成 Action 覆盖，也没有实际子调用；不能用它证明语义 Action 干预或子策略生成已被这次真实模型业务过程验证。

一次规划工具命令混用已被观察到，但运行随后继续完成交付。规划状态推进与方法调用次数只作为诊断信息；不因本例 Planning 调用较少或沿用原生 Action 判定业务失败。是否需要调整生成策略，应由下面的实际任务结果决定。

### 业务输出与限制

首次任务产生招聘方案、JD、结构化面试安排、评分表和虚构履历证据对照。需求变更轮调整了 Go 要求、时间窗口和相关材料，并通过 deliver_files 实际交付 7 个文件。没有观察到平台登录、职位发布或联系候选人的动作。

Execution.errors 两轮均为空，但首轮仍有两个可恢复工具失败：错误尝试未配置的 Skill Hub，以及规划工具命令不符合 schema。这表明框架错误汇总与工具失败、业务质量应分别核查。

业务表述仍有缺口：用户明确要求 45 天到岗，输出部分里程碑仍以 offer 接受为终点，并再次要求确认这一口径。不能仅以进程 completed 或输出文件数量宣称任务全面满足。

## 7. 已确认机制问题的修复与定向复验

用户要求优先修复代码和设计机制问题后，完成以下调整：

- Planning 接受相同 ViewT、仅含 view/guidance 的具名投影子类。宿主先验证声明类型，再归一化公共投影；不同 ViewT 或额外包裹字段仍拒绝。
- Planning 工厂提供只读 plan 依赖，与其他策略一致。初始化前返回 None；之后返回当前会话已提交视图的副本，不暴露当前操作的未提交状态。
- 共同方法类型解析在缺少注解时返回带策略/方法/参数名的 TypeError，保留具体类型要求，避免原始 KeyError。
- Plan.node_reasons 的 schema 与根生成提示明确节点键格式和空节点情况，并澄清 requirements 选择子定制、实际调用独立决定。

定向单元检查：67 项通过，覆盖规划绑定、能力绑定、跨策略交互及策略契约。新增回归包括子类型初始化/查询/恢复、不同 ViewT 拒绝、额外投影字段拒绝、工厂只读视图的会话隔离及未提交状态隔离、缺注解的具体错误提示。

原始模型代码复验位于 /tmp/raven-curator-mechanism-replay-20260929-144418/。旅行和小红书的原始候选文件摘要保持一致，两份 Planning 实现均通过修复后的绑定与初始化。该项只证明原始失败点已解除，不计为重新完成整个 Curator 生成或客户业务验收。

本次不扩大模型预算，不重跑整批生成。招聘的工具使用质量、规划参与程度和业务口径问题保留为后续效果改进项。

原生集成收尾：当前输入先更新规划再影响能力选择/指导撤回，以及父 Playbook 调用实际 ACP 子进程两项检查通过（2 passed，11.64 秒）。该检查使用确定性模型回放。源码 lint、差异空白、源码语言与文件门禁检查通过。

### 第二轮新增的上下文压力衔接问题

旅行第二轮失败于 Memory 投影额度检查，原始输入估算 88,718 tokens，额度 87,601，添加台账后 89,770。原生 emergency_shrink 可将原始输入降至 49,032，且保留全部 required 消息；问题是 Adapter 的 ValueError 先于原生模型溢出恢复，使这条路径无法进入原生压缩。

采用将本地投影超限转换成明确、可记录的原生 context-overflow 响应，由 Loop 沿用自己的收缩与重试预算。相比要求每个生成实现复制压缩器，或在 Adapter 内另建重试循环，该方式保持已有职责和预算。消息/来源校验失败仍保持异常，不伪装成压力；原生无法收缩时仍明确失败。原始业务失败记录保留，不因输入复验通过改记业务成功。

修复已落地。定向验证共 14 项通过：跨策略/上下文边界 13 项，以及真实 Worker/Loop 的本地压力恢复集成检查 1 项。后者使用确定性 provider，验证投影超限后沿用原生工具输出收缩，保留客户请求并返回最终回复，只有两次真实 provider 请求；本地超限另记 model.input.pressure。保护来源错误仍抛出，不误分类成压力。

另用旅行原始生成源码、保存的失败 ContextRequest 和会话检查点复验，未改生成代码：原生收缩移除 38 段旧工具输出正文，必要消息和来源校验通过，重新 compose 为 49,958 tokens，低于 87,601 额度。检查点与失败瞬间投影的台账长度略有差异，因此这个复验的压缩前投影为 89,644，而原始故障记录为 89,770。结果保存于旅行目录 pressure-replay.json；未重新调用 DeepSeek 完成第二次业务请求。

本轮没有增加生成预算，也没有为凑齐策略覆盖补写生成代码。三例最终产物和事实/资源约束问题保留为后续效果优化依据；旅行原始运行仍记录执行失败。
