# Rubric 构建经验闭环实施方案

本方案说明 Rubric 构建侧如何积累、验证和使用构建经验，以及如何接入管线共用的准入与修订协议。已有经验闭环保留，公共协议接入、实际使用记录和归因修订增强已经实现。

上层指引：[Harness 管线经验准入与修订设计](experience-governance-design.md)。并列方案：[Curator 经验闭环实施方案](curator-experience-plan.md)。准则本体和层次化构建仍由[层次化 Rubric 设计](hierarchical-rubric-design.md)约束，本方案不重新定义 rubric。

## 目标与当前状态

学习对象是“如何构建和修订可用的 rubric”，消费角色是 Rubric Builder。Meta Reviewer 从评价记录中提出局部评价问题和可复用经验；局部问题驱动本次 rubric 返修，经验进入后续构建指导，两条路径分别管理。

| 能力 | 当前状态 |
| --- | --- |
| 原则和方法候选 | 已实现，含适用范围、来源评价记录及可选替换对象 |
| 保存及采用 | 已实现候选保存、独立回放比较、采用记录、替换和回滚 |
| 后续构建使用 | 已实现按范围选择生效条目并注入 Builder |
| 层次化 rubric 的局部修订 | 已实现版本绑定、受限操作、父子关系和独立修复验证；不是经验正文修订的替代流程 |
| 公共经验协议接入 | 已实现，共享 Governance、实际指令绑定及旧记录隔离迁移 |
| 标准化经验评审和归因修订 | 已实现类型说明、持久诊断、受限替换、来源撤销和验证后回滚 |

既有实现位于 experimental/harness/assessor/guidance.py、reviewer.py、validation.py 和 standard.py。已有记录及测试继续保留，不能因为抽取公共模块而把现有闭环视为未实现，或把公共设计草案描述为已接入。

## 闭环角色与运行时序

| 职责 | 承担者 |
| --- | --- |
| 使用构建经验生成或修订准则 | Rubric Builder |
| 评价产物并保存判定依据 | Assessor 及具体检查器 |
| 诊断评价问题并提炼经验候选 | Meta Reviewer |
| 固定回放、核对证据和决定采用 | 宿主及领域验证策略 |
| 版本、使用记录和修订约束 | GuidanceStore 内嵌的公共 Governance 协议 |

正常调用顺序：选择当前生效指导并固定内容 → Builder 构建或复用 rubric → 冻结证据并评价 → Meta Reviewer 提交 issues、guidance_issues 与 guidance → guidance 候选经过独立验证 → 后续构建调用使用已采用的新版本。

本次 issues 可按既有权限触发一次有界 rubric 返修。新增 guidance 即使通过采用，也不改写已开始的构建调用或已冻结的评价；验证时在隔离回放中试用，后续正常构建才使用新指导。

没有候选时保留原指导；没有独立验证材料时只保存候选；验证失败或不确定时原生效版本继续有效，除非另有证据触发停用。源要求更新与指导更新分别记录，不能用新要求造成的判定变化冒充指导收益。

## 经验表达与适用范围

沿用 principle 和 procedure。其含义、价值和固定使用说明由总纲定义，并实际出现在 Builder 的指导上下文中。原则正文表达适用情境、判断依据和理由；方法正文表达触发条件、步骤及检查与停止。不要求每条原则配一个方法。

例：原则是“以原始要求核对覆盖，不能仅检查现有子项”；方法是“提取需覆盖的要求、映射已有节点、找出遗漏、在允许范围内补充、用有效案例和反例复核”。它们指导构建过程，不直接成为任务的门控条件。

保留现有 kind、scope、text、episodes、replaces 的职责。公共层增加的角色、版本和使用关联由宿主管理，不要求模型反复填写能从调用上下文确定的信息。需要更精确的任务范围时，由领域适用性规则解释，不能把历史 task 或 * 的字符串直接当成跨角色授权。

当前最多选择八条生效指导，按类型与身份稳定排序；这是有界选择，尚不是语义检索。接入时继续采用完整条目预算，加入固定说明，并记录实际条目及渲染版本。验证和正式使用必须经过相同的渲染路径。

经验正文不携带隐藏答案、检查明细或客户特有事实。需要核查原始依据时使用评价侧受控记录，不向 Curator 或 Worker 传递原始评价材料。

## 准入评审与效果验证

每条候选应说明希望纠正哪类构建问题或增加什么能力，以及在哪些情境下成立。可以在现有正文和评审记录中表达，不先增加一套大字段表。引用存在只能证明来源可定位，内容评审还要检查来源是否支持该概括。

内容评审检查任务要求是否被偷换、适用范围是否过宽、原则是否存在反例、方法是否具有可执行步骤与停止条件，以及与已有指导是否重复或冲突。模型评审意见可以拒绝或要求修改候选，但不能替代独立效果验证。

既有采用规则继续保留：同时具备独立正例和反例；新指导的判断不含未知；至少一项判断改善，且已正确判断的案例不回退。跨任务候选还要求跨任务案例和未参与提炼、未被此前验证使用的输入。该规则服务评价准确性，不作为所有角色的公共硬编码。

验证固定当前指导基线和候选，实际重新构建 rubric 并进行评价，保存前后构建、检查和判定记录。旧 rubric 的得分变化、模型相互认同及单纯修改最终标签，都不构成指导有效的证据。

增强项是在最终判断之外核对候选声称改进的性质。例如，覆盖完整性经验需要检查原始要求到节点的覆盖；层级归属方法需要有效细化和错误挂接两类案例。检查用独立来源、程序约束或事先固定的判断依据，不让候选自行定义自己的正确答案。

原则重点验证判断依据和边界，方法重点验证关键步骤、结果分支及停止条件。方法被放进上下文并不证明被正确运用，缺少执行证据时不作强归因。

首轮公共化不放宽现有采用规则。若以后允许在准确性不退化前提下合并重复指导，应作为单独的版本化策略，预先定义等效性和上下文成本目标，不能通过修改原规则来追认某次失败候选。

## 归因修订与恢复

评价问题先定位到准则内容、检查器、证据、构建指导、指导选择或生成执行。Meta Reviewer 的 issues 针对评价装置，guidance_issues 针对经验。后者引用宿主提供的经验身份、依据、原因及允许修改的字段；不能从准则失败直接跳到改写指导。宿主保存未解决诊断，后续评审窗口缩短或模型不再提及都不会消除它。

经验修订形成绑定基线的候选变更，注明涉及条目、允许改变的部分、支持证据和验证目标。新措辞、适用范围扩大或方法合并都生成新版本，经验证后替换；未涉及条目保持不变。replaces 可保留为简单替换入口，多条合并需要明确所有受影响对象。

例如，遗漏要求可能来自原则表述错误，也可能来自所需材料未提供。若是材料缺失，应补足证据或输入，不能修改正确原则。指导没有加载时修复选择与渲染；生成未执行方法时检查方法或生成过程，保留尚不能确定的原因。

回放范围覆盖相关共同生效指导和受保护条件，写入范围仍限制在被归因的部分。重复同一候选与同一证据不得靠重试寻找偶然通过；获得新证据或改变候选后再生成新验证记录。

来源撤销、定义变化或可信反例可以触发停用与复查。恢复旧版本前核对其依据和适用性；不能因回滚而重新启用失效经验。当前替换和回滚历史应迁移保留，既有 retired 状态按原语义保留为历史兼容数据，对外使用停用或被替换的表达。

## 公共协议接入与完成条件

| 顺序 | 工作及完成条件 |
| --- | --- |
| R1 固定兼容基线 | 核对候选、采用、回放、替换和恢复记录；保留旧文件及既有结果，候选不能因迁移生效 |
| R2 接入公共生命周期 | 将来源、版本、决策和使用记录接入公共协议，准确性验证仍由评价侧策略承担 |
| R3 完善指导表达 | 实际加入原则和方法的定义与使用说明，固定渲染及条目预算，验证与正式调用读取相同内容 |
| R4 接入经验归因修订 | 将诊断关联到使用版本，限制局部变更并验证相关组合，支持来源失效与受控回滚 |
| R5 完成回归与独立验证 | 原有门控、外部要求和层级修订行为不退化；新协议通过本方案的验收场景 |

首轮保留 JSON，使用 schema 2 内嵌公共治理记录。旧字段用于兼容展示，必须与权威治理记录一致；旧 adopted 条目缺少新收据时保留历史并按候选处理，不静默追认。来源快照、已用验证输入和替换历史继续保留。

主要修改点是 assessor/guidance.py、reviewer.py、validation.py、standard.py 及 builder/review 提示词。公共状态管理与 Curator 共用；标准内容、回放语义及检查器继续归评价侧所有。

验证复用 tests/test_assessor_guidance.py、tests/test_assessor_reviewer.py、tests/test_assessor_hierarchy.py 等已有入口，新增测试围绕真实行为边界。真实模型验证沿用获准配置，缺配置明确跳过。功能测试通过只能证明实现遵守协议，不能直接宣称构建质量已在所有任务上提升。

## 验收场景

| 场景 | 预期结果 |
| --- | --- |
| 当前评审提出新指导 | 保留候选，已开始调用的上下文不改变 |
| 候选只有模型赞同 | 不正式采用 |
| 正反例有改善且无回退 | 满足其余策略条件后采用，保存前后实际构建记录 |
| 跨任务证据重复输入 | 不被计为新的未用输入 |
| 经验涉及保护的外部要求 | 不能削弱原要求或改变其权威 |
| 指导正确但未被加载 | 修复加载路径，不无依据地重写经验 |
| 局部经验修订 | 无关条目不变，相关组合通过回归 |
| 采用前基线或渲染发生相关变化 | 旧验证不能无条件批准新版本 |
| 迁移或暂停恢复 | 可追溯原来源与采用依据，候选保持候选 |
| Rubric 与 Curator 同时接入 | 公共生命周期共用，评价证据和准入规则不会跨角色混用 |

完成公共接入以这些可观察行为为准；层次化 rubric 的既有验收仍然独立有效。

## 已实现的调用与验证边界

GuidanceStore.consider 保存候选和诊断；adopt 要求 Validation 对应实际渲染的 before_instructions 与 after_instructions。Builder 请求前保存 guidance_usage，安装 rubric 前重查来源和策略。局部修订只能改变诊断授权的字段；加载故障不能通过内联 correction 扩大为正文修订。

同一候选与同一证据不会无限重试。来源撤销会停止相关指导；回滚替换必须重新比较当前组合与拟恢复组合，旧采用记录本身不足以恢复旧版本。

回归覆盖指令冒用、重复留出输入、跨任务范围、持久诊断、并发写入、存储失败、来源失效和真实 Builder 请求中的使用。层级结构、外部门控和独立验证仍由原评价系统负责。

具体领域的覆盖率、父子归属或其他性质需要宿主给出独立案例与验证依据；通用准确性回放本身不能证明所有这些性质。缺少相应材料时，不授予超出已有证据的改善主张，也不让 Meta Reviewer 自己生成正确答案来补足准入。
