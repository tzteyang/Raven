# 层次化 Rubric 构建与增量修订实现设计

设计与实现日期：2026 年 10 月 9 日。状态：已在独立功能分支实现，本文同时保留需求契约和实际接入说明。

本版在现有评价系统上增加可变深度的准则层级，以及由问题归因限定范围的增量修订。目标是让构建者和元评审能够解释：一条准则为什么存在、属于哪个要求、为何继续细化、为何修改，以及修改是否改善了评价。树的深度、节点数量和评价器自己的通过率都不作为成功指标。

本文记录已讨论确认的需求，并给出具体实现选择。构建预算的数值等运行参数尚需实测确定；这些参数不改变本文的语义与权限约束。基础评价系统的已实现契约见 `experimental/docs/evaluation-system-design.md`。

## 1 当前基础和需要补齐的能力

当前已有 `Criterion` 的 definition、basis、assessment，来源版本绑定，gate／guardrail／quality 类型，外部要求保护，`add / rewrite / remove` 修订，Assessor、Meta Reviewer、构建指导沉淀和独立晋级验证。`remove` 从当前 rubric 移除条目，历史证据和修订记录保留。

本次已补齐 parent_id、动态细化队列、关系审查任务说明，以及对所有修订理由生效的节点和字段权限。原有“换用其他理由即可修改范围外条目”和“检查器修复夹带定义修改”的入口已经关闭。结构与权限由宿主校验，语义归属由构建和元评审按第 4 章的方法判断；程序并不自动证明自然语言蕴含关系。

基础实现的历史测试结果与本次新增验证分开记录；实际接口、验收证据及实证限制见第 12 章。

## 2 代码实现必须满足的需求

以下编号用于关联实现与验收，不需要写入每条 Criterion。

| 编号 | 必须满足的需求 |
| --- | --- |
| R01 | 使用一份结构化 JSON 表达 rubric。所有层级使用同一种 Criterion；只增加必要的父关系，不另存一套可执行树。 |
| R02 | 深度按需变化，不限定两层，不强迫各分支同深。横向是同一父范围下补齐并列项，纵向是细化已有项；顶层新增也是横向扩展。 |
| R03 | coarse／fine 是相对语义粒度，不能与横向／纵向永久绑定。新节点的位置必须依据要求之间的关系判断。 |
| R04 | 每条准则有任务或材料依据；引文存在、处于某个层级、模型间同意，都不能代替语义正确性或独立验证。 |
| R05 | 生成采用有预算的节点处理流程。停止、无法取证和预算耗尽必须区分；停止运行不等于覆盖完整。 |
| R06 | 外部要求的原义、范围和强度受保护。没有外部评价时模型门控仍可工作；模型后续补充不能削弱外部要求。 |
| R07 | 修改先有问题依据和影响范围，再有补丁。所有 add／rewrite／remove 都受宿主固定的操作、位置和字段限制；理由名称不能扩大权限。 |
| R08 | 区分 Worker 缺陷、准则缺陷、核验错误与证据缺口。Worker 违反合理要求不能成为降低准则的理由。 |
| R09 | 每次评分使用固定版本，保留前后结果；修订记录绑定基础版本和输入版本，拒绝过期补丁。 |
| R10 | 保留父节点整体判断，子项全过不自动推出父项通过；质量不能抵消门控或护栏失败，必要未知不能记为通过。 |
| R11 | 保留有界元评审和原则／步骤沉淀。模型提出的方法改进仍需独立验证后才能成为后续构建指导。 |
| R12 | 修改历史可追溯，范围外内容保持不变；同一缺陷不能因父子重复报告被当作多次独立失败。 |
| R13 | 老记录的含义与证据保留，缺失的层级关系不能靠猜测恢复；隐藏评价数据继续遵守原有受众边界。 |
| R14 | 以遗漏、误判、有效解法保留和下游反馈质量验证价值；单元测试只能证明实现约束，不能证明真实模型判断质量。 |

继续使用 Rubric Builder、Assessor、Meta Reviewer 三个评价角色。宿主负责预算、结构校验、权限和版本控制；Analyst 合并反馈；Curator 负责 Worker 的机制归因与 harness 改进。

## 3 层级 JSON 和每个字段的职责

### 3.1 唯一结构

`Standard.criteria` 继续是 Criterion 数组。Criterion 新增 `parent_id: str | null`；null 表示该节点直接属于整个任务范围。顶层可以有多条准则，因此整体是一组树。任务范围由现有 task 表达，不再额外创建一个具有独立评分的虚拟 Criterion。

每个节点沿用 id、origin、authority、kind、definition、basis、assessment。内部节点和叶子都具有完整语义；粗准则并不是只填写一个标题的半成品。

父子关系只保存一次。嵌套 children、节点深度和路径由读取方生成；不再保存 coarse／fine 标签、展开方向标签、层级权重或重复的接受条件。程序核验是 assessment 的内容，不算下一层准则。

### 3.2 JSON 示例

下面展示 schema 3 中两条完整准则。示例材料 pricing_policy 的内容是 `The quote must include all mandatory fees and taxes.`；version 为宿主按现有 digest 方法计算的内容摘要。实际运行中模型不得自己填写版本。

```json
{
  "schema": 3,
  "criteria": [
    {
      "id": "fees_complete",
      "parent_id": null,
      "origin": "derived",
      "authority": "model",
      "kind": "gate",
      "definition": {
        "subject": "Delivered quote",
        "applies_when": "A price quote is requested.",
        "acceptance": "Include every mandatory fee and tax required by the supplied policy."
      },
      "basis": {
        "references": [{
          "source": "pricing_policy",
          "quote": "The quote must include all mandatory fees and taxes.",
          "version": "4b01d2eba0269d4946f378a570e52d46a2e93b1b1dabe6212ae69f8e59974136"
        }],
        "derivation": ""
      },
      "assessment": {
        "decision": {"method": "llm", "instruction": ""},
        "required_checks": [],
        "evidence_requirements": [
          {"kind": "delivered_text", "reference": "quote.txt"},
          {"kind": "material", "reference": "pricing_policy"}
        ]
      }
    },
    {
      "id": "tax_included",
      "parent_id": "fees_complete",
      "origin": "derived",
      "authority": "model",
      "kind": "gate",
      "definition": {
        "subject": "Tax coverage in the delivered quote",
        "applies_when": "A price quote is requested.",
        "acceptance": "Include every tax required by the supplied policy."
      },
      "basis": {
        "references": [{
          "source": "pricing_policy",
          "quote": "The quote must include all mandatory fees and taxes.",
          "version": "4b01d2eba0269d4946f378a570e52d46a2e93b1b1dabe6212ae69f8e59974136"
        }],
        "derivation": "Tax coverage is a necessary part of complete mandatory cost coverage."
      },
      "assessment": {
        "decision": {"method": "llm", "instruction": ""},
        "required_checks": [],
        "evidence_requirements": [
          {"kind": "delivered_text", "reference": "quote.txt"},
          {"kind": "material", "reference": "pricing_policy"}
        ]
      }
    }
  ]
}
```

这里的子项只核验税费覆盖，不能证明父项要求的全部费用已经覆盖。其他必选费用是否遗漏仍属于父节点整体判断。

### 3.3 结构和继承边界

宿主必须检查 ID 全局唯一、父节点存在、无自指和循环；同一次应用完成后不能存在孤立节点。ID 由宿主分配并保持稳定。首版新增节点只能引用补丁基础版本中已存在的父节点；新子节点获得 ID 后，才可在下一次受控补丁中继续细化，避免引入临时 ID 解析机制。

深度不决定权威、强度或适用条件。子项必须明确自己的定义和依据；不能凭父节点是 external 就获得 external 权威，也不能凭挂在 quality 下就豁免一项有独立依据的硬要求。父子适用范围是否一致由关系审查核对，执行时不隐式合并定义。

跨分支护栏可以保留为共同范围中的一条准则，不复制到每条分支。父子关系不表示因果关系，也不授予修改祖先、后代或兄弟项的权限。

## 4 怎样确定横向补齐和纵向深化

### 4.1 构建前先做关系判断

每个候选条件依次经过以下判断，结果和依据写入本次构建记录，复用 Change.explanation 与 basis.derivation；不为每个判断步骤增加 Criterion 字段。

1. **确认任务依据。** 它对应哪项原始要求；引用或推导是否支持它。模型生成的父节点不能成为唯一依据。
2. **排除重复与核验手段。** 已有接受条件相同，则保留或澄清原项；只是增加重算、查文件等核验动作，则更新 assessment。
3. **检查细化关系。** 在共同适用情境下，父要求已满足时，候选条件是否仍可以合理地不满足。
4. **选择父范围。** 找到语义范围最贴近、能够支持这项细化的既有节点；独立义务放在共同上层作为并列项。
5. **提出局部补丁。** 说明与兄弟项的区别、补足的内容以及预期改善；不得因需要层级而制造新义务。

对于本版的必要条件细化，违反子项应当能够说明父要求某个部分未满足；子项成立通常只覆盖父要求的一部分。若父要求可以被有效满足而子项失败，则该父子关系需要否定或重新定位。若二者基本等价，通常属于重复、澄清或核验改进。

这是受材料约束的语义审查，不是通用定理证明。Meta Reviewer 寻找有效反例；找不到反例不等于证明成立。无法确定关系时保留待审提议，不强行挂到更深层。若候选有独立任务依据，可以在获准的共同范围中作为独立项处理。

### 4.2 方向是相对位置

| 当前结构和候选 | 正确解释 |
| --- | --- |
| 整个任务下新增预算约束 | 顶层横向扩展；不存在第三种顶层方向 |
| 费用完整下面已有住宿和交通，补充税费 | 横向补齐并列子项；相对于费用完整又是更 fine 的条件 |
| 将住宿费用完整展开为住宿夜数、房间数量等有依据的条件 | 相对于住宿节点纵向深化 |
| 为税费条件增加一个计算验证器 | 核验方案修改，不创建下一层业务准则 |

选择位置依据 subject、applies_when、acceptance 与原始来源，不能仅根据关键词相近、句子长短或树的深度。例如预算内与费用完整是不同义务；费用全部列齐仍可能超预算。

## 5 动态构建的控制流程

### 5.1 首次与后续入口

宿主固定任务、材料版本、外部要求、当前 rubric、可用核验器、相关评价问题和已采用指导，创建候选副本。首次先让 Builder 提出覆盖关键义务的完整粗准则，再检查哪些节点值得细化。

后续只由可解释的事件触发：材料或外部要求变更、具备证据的评价缺陷，或已记录且本轮有预算继续处理的构建任务。单纯 Worker 失败、评价分数下降、树不够深、或没有新信息的同一取证失败，不能自动触发全量重写。新指导被采用也不自动授权修改所有既有准则。

缺项定位到父范围，已有问题定位到具体节点和相关字段。任务根范围可用于新增顶层项；层级关系缺陷需要明确涉及的节点和连接。

### 5.2 有预算的节点队列

队列属于构建运行状态，不属于业务准则。一次待办必须说明目标范围、问题依据、允许的操作和字段。Builder 读取目标、必要的祖先／兄弟上下文、相关原始材料及指导，在一次调用中返回局部补丁，或说明无需继续处理。

宿主优先处理外部要求覆盖、门控／护栏缺口和已确认误判，再处理一般质量细化。每次只授予当前待办的修改范围。合法补丁应用到候选副本，并把有明确继续处理理由的子项加入队列；已充分表达的分支停止。非法补丁不应用，重试消耗预算。

构建同时受模型调用次数和新增节点数限制，不以深度作为目标。每次调用，包括拒绝后重试，都计入预算。没有实际变化或同一问题在相同输入下重复出现时，停止该待办，避免空转。数值上限作为宿主配置，先用案例调试确定。

队列清空表示没有已知待办，不证明绝对完整；预算耗尽表示停止运行，必须保留未完成事项。记录区分完成、保持、取证不足、预算耗尽、修订拒绝等停止原因。不要根据有没有 children 推断节点是否已充分细化。

### 5.3 固定版本和有界评审

实现选择是复用现有 Assessor 的单次元评审位置：候选结构生成后，先固定候选版本；有任务产出时用它试评，再让 Meta Reviewer 同时审查原始要求、树结构和实际评价记录。这样可以检查真实误判，并避免在每个节点、每个层级另加一轮模型评审。

顺序为：输入快照 → 首次粗建或局部待办 → 有界队列处理 → 固定候选版本与试评 → 一次元评审 → 至多一次定点返修与必要重评 → 输出版本、Signal 和未解决事项。

尚无任务产出时可以保存构建候选并检查结构，但不能声称已经验证评价准确性。结构性问题与运行中发现的问题复用同一 Issue 机制。元评审后的返修不再进入另一轮完整评审循环；未解决问题留在记录中，等待新证据或下一次合法构建事务。

每次试评和重评都固定其 rubric 与证据版本，分别保存结果。发现新的问题不允许在同一次评分中悄悄换标准。构建、当前试用、验证有效、稳定 harness 晋级是不同结论，不能互相替代。

## 6 由归因限定的增量修订

### 6.1 先确定修复对象

| 问题归因 | 修改边界 |
| --- | --- |
| Worker 违反合理准则 | 进入 Analyst／Curator；保持准则 |
| 某父范围缺少应覆盖的要求 | 允许在该范围 add，不顺带重写兄弟项 |
| 已有条件过粗且拆分有诊断价值 | 允许在指定节点下 add 子项，保留父项整体含义 |
| 定义或适用条件错误 | 允许 rewrite 指定定义字段及确有需要的依据 |
| 核验器错误 | 限定为对应 assessment 部分，冻结接受条件、类型、权威和父关系 |
| 缺少证据 | 补证或 unknown；不得以不可观察为由删除必要要求 |
| 重复或无依据条目 | 有证据后允许 remove 指定项，同时检查覆盖和子项引用 |

### 6.2 宿主固化修改范围

在 Builder 生成补丁之前，宿主根据归因提案和保护规则固定本次允许范围。元评审应保留 target 的结构化含义，不能再把 rubric 与 check 问题压平成不区分类型的纠正字符串。模型可以提议范围；补丁执行时不能自行扩大它。这不要求人工逐轮审批。

建议复用 Issue 的 criterion、target、evidence、correction，在构建事务中增加一个宿主管理的允许清单。下面是控制记录示意，不是 Criterion 的新增字段：

```json
{
  "base_version": "rubric-v7",
  "issue": {
    "criterion": "fees_complete",
    "target": "rubric",
    "evidence": "assessment-12: a policy-required tax was omitted but the quote passed",
    "correction": "Add the missing tax-coverage condition under fees_complete."
  },
  "allow": [
    {"op": "add", "parent_id": "fees_complete"}
  ]
}
```

base_version 绑定被修改的版本；issue 解释问题依据；allow 才决定写入范围。运行中证据引用必须能定位到真实来源或评价记录，示意文本不能直接成为独立验证标签。

允许清单对 add 指定父范围，对 rewrite 指定条目 ID 和字段路径，对 remove 指定条目 ID。新增项、结构连接、定义和核验方法分别接受实际差异检查。ID、origin、authority 等宿主字段不能由普通模型补丁修改。类型变化也必须有明确范围和来源依据，不能隐藏在普通核验修复中。

reason 仍用于解释 new_norm、uncovered、undecided、imprecise、beyond_norm、duplicate、review 等原因，但任何 reason 都不能绕过允许清单。必须覆盖已发现的反例：只允许修复 C1 时，使用 imprecise 改写 C2 也应拒绝；只允许改 C1.assessment 时，顺带修改 C1.definition 也应拒绝。

### 6.3 应用与复查

整份补丁先验证再原子应用；出现越界、过期基础版本、无效来源或非法树结构时，不部分写入。scope 外准则的规范化内容必须保持一致；变更日志不能仅依赖模型自行宣称的修改列表。

复查范围可以大于修改范围。父目标变更后，相关子项进入一致性复查，不默认重写；子项出错可以触发父项覆盖复查，不自动改父项；共享材料变更触发实际引用它的节点复查，不能因此授权全部条目更新。

remove 不做隐式级联删除，也不偷偷把子项移到别的父节点。非叶节点移除必须显式处理相关引用，并逐项获得相应修改范围。重新挂接关系也必须出现在允许的差异中。

现有外部准则仍整体受模型写保护。新的外部要求通过宿主既有接入机制更新并重新判定。自动发布外部准则核验修复不作为本版附带功能。

## 7 层级评价和修改有效性

Assessor 继续使用每个节点自身的完整 definition、basis 和 assessment。父项保持整体判断；子项通过不自动汇总为父项通过。全不适用不等于验收，缺证或核验失败不能变成通过，质量项不能抵消硬性失败。

父项通过但某个必要子项有明确违例时，属于需要处理的判定或关系冲突，不能以父项通过覆盖子项证据。已观察到的程序失败必须保留；只有独立证据确认检查器有误并验证修复，才可以形成新的判定，旧失败记录不能擦除。

父子重复描述同一缺陷时，Analyst 以最具体且有依据的行为差距组织反馈，保留父目标作为上下文。Curator 仍接收其有权读取的行为要求，不获得隐藏评分规则、验证实现或保留案例答案。

修订验证固定任务输入、产出证据、受保护要求和核验配置，比较旧、新准则对目标缺陷、有效替代解法及相关回归案例的表现。模型自造反例可用于探索，但不能自行提供权威预期标签。更深的树、更多的节点或更高的自评分不能证明改进。

修订范围、改动内容和验证结果绑定同一候选版本。程序校准继续绑定它实际核验的定义、依据和方案；关系变化若改变了真实判断上下文，则重新校准。整体修订采纳与指导采用的验证结果还需绑定对应完整版本，不能移用于后续改写。

需求本身变化时，先固定新的适用验收协议，再验证新准则；不能把新要求导致的通过转失败直接称为评价更准确。没有可靠预期的修改可以保存和试评，但标记为尚未验证；必要的未解决评价问题继续阻止完整验收或稳定晋级。

现有节点通过率会受细化数量和父子重复影响。界面可以展示逐项结果，但不得把不同层级版本的节点通过率直接作为性能趋势；效果比较使用固定、独立的任务或属性验证。

## 8 构建方法本身怎样持续改进

保留原有 Episode → Principle／Procedure 候选 → 独立对照 → 已采用构建指导的闭环。一次遗漏不自动变成通用规则，反复出现也不自动增加权威。

例如，费用完整性判断遗漏了原始材料明确要求的税费。可提炼的原则是“完整性检查应从原始要求核对覆盖，不能只遍历现有子项”；可提炼的步骤是“列出要求 → 对照子项 → 定位缺口 → 局部补齐 → 验证缺陷和有效变体”。“所有任务都检查税费”则不具有相同的泛化依据。

指导仍使用现有 principle／procedure、任务范围和记录引用。适用条件写在指导内容中，不给每一层复制一套方法论字段。已采用指导用于选择构建和修复方法，不能扩大本次写入范围或覆盖外部要求。方法验证应实际运行新的层次构建流程，确认后续请求消费了指导，而不只保存一条采用记录。

## 9 模块改造和记录兼容

| 位置 | 已接入的改造 |
| --- | --- |
| `assessor/rubric.py` 与 `standard.py` | 增加 parent_id；全局结构校验；保留完整节点判定；版本快照与未解决事项 |
| `assessor/builder.py` 与 Builder 提示词 | 关系判断、受控节点队列、补丁范围与字段校验、稳定 ID、停止原因 |
| `assessor/reviewer.py` 与 Reviewer 提示词 | 审查节点及细化关系；保留问题类型和具体范围；禁止靠换理由扩大修改 |
| `assessor/standard.py` 的审核路径 | 复用一次元评审和一次定点修正；固定证据重评；不能仅凭条目发生变化就宣称问题已解决 |
| `assessor/guidance.py` 与 `validation.py` | 复用已有经验和独立验证；让重放实际执行新构建流程并绑定对应版本 |
| `iteration` 与 Analyst 交接 | 保留外部接入、证据受众和 Curator 分工；合并父子重复反馈 |
| WebUI 记录读取与展示 | 从 parent_id 生成树视图；展示未展开、未判定和未完成的真实原因；按版本查看局部差异 |

优先扩展现有模块，不增加独立服务、图数据库、通用证明器或树形加权评分引擎。具体宿主控制对象保持最小；只有执行、恢复或验证实际消费的字段才加入持久记录。

新保存格式使用 schema 3。schema 2 已具有完整语义字段，可以作为平面森林读取，缺少的 parent_id 设为 null，不能自动编造分解关系。更早缺少 definition／basis／assessment 的记录继续只读展示，执行前从原始材料重建。旧 retire 修订记录按 remove 展示，原始历史保留。

恢复时校验候选基础版本、来源摘要和指导版本。旧进程中的写入范围不能跨版本直接复用；来源变更后重新定位影响范围。历史验收结果不自动成为新版本的有效验证。队列只保存恢复所需的目标、原因和进度，不重复存放完整的第二份准则体系。

与目标功能分支集成时，保留“老板只评分”的度量模式：只度量的信号不能进入 Analyst、构建修订、停止判断或 Curator。显式交给交互闭环的外部要求继续按原有机制保护。合并前需要基于目标分支的最新状态验证这一区别。

## 10 实施顺序与验收场景

实现按以下四步完成，并分别提供行为验证。提交、推送和合并仍需用户明确要求。

1. 增加唯一父关系、JSON 校验和记录兼容，保持原有评价语义。
2. 完成宿主范围对象与原子补丁校验，先关闭越界修订入口。
3. 接入动态队列、关系判断、停止条件，以及有界元评审和针对性重评。
4. 接通指导重放、Analyst 去重、WebUI 与端到端案例，评估层次化是否确实有价值。

## 11 完成判定

实现完成需要满足 R01 至 R14，并为 A01 至 A15 提供可检查结果。交付时应能从一次错误评价追溯到问题依据、归因范围、具体节点补丁、受保护的未改内容、固定证据的前后比较和后续采用状态。

具体预算上限、一次处理单节点还是同一允许范围内的小批节点，以及界面默认展开深度可以根据案例调整。JSON 的唯一性、来源保护、关系判断、修改权限、固定版本和独立验证边界不得随这些参数变化。


## 12 实际接口和验收记录

实现位置仍为既有评价模块。Criterion 只新增 parent_id；修订权限由新增的 assessor/revision.py 中 RevisionScope 和 Permission 承担。Builder 默认每次构建最多 4 次模型调用、16 个新增节点；截断、格式错误和被拒补丁的重试均计入调用预算。这是单次构建上限，允许宿主按实际任务配置。

Change.refine 保存继续处理该节点的理由，宿主据此安排后续局部任务。已有节点只有同时获得子项新增权限时才能申请继续细化；定点返修不能启动递归展开。空修订必须给出停止原因或明确的材料未处理说明。队列优先处理必要条件，纯质量细化的未完成状态不会独自阻断任务验收。

待办保留目标及祖先的内容摘要。无关回归项加入 rubric 后，可以在确认相关内容未变的前提下重新绑定当前版本继续该分支；来源、指导或相关节点变更会使旧任务失效并留下记录，不能沿用旧权限。被诊断的评价缺陷另存 open_issues，不因任务失效、一次空评审或修改了文字而自动消失。中断未发布的构建会回滚其活动状态，保留作废候选记录，恢复后从上次已发布版本继续。

独立验证使用 RepairSuite，显式区分“修复哪个问题”和“核验哪个属性”。例如，修复税费检查器必须给税费准则提供独立正反例；不能拿整任务失败标签推断这个检查器正确。关系调整或删除可以核验受影响的父范围。配置示意：

```python
from experimental.assessor.builder import RubricBuilder
from experimental.assessor.standard import Assessor
from experimental.assessor.validation import RepairSuite

assessor = Assessor(
    provider,
    standard,
    norms=materials,
    builder=RubricBuilder(max_calls=4, max_nodes=16),
    reviewer=reviewer,
    repair_suites={
        "tax_included": RepairSuite(
            criterion="tax_included",
            cases=host_verified_cases,
        )
    },
)
```

其中 provider、standard、materials、reviewer 和 host_verified_cases 由宿主提供；cases 是 ReplayCase 元组，预期由独立 verifier 产生。验证绑定基础、候选和案例版本，要求修复后的属性判断与全部所选独立结果一致，并保留改进和无回归证据。相同候选和案例不反复验证以等待随机通过；后续新增独立案例时，可以验证先前的候选而无需制造另一项代码或准则修改。

有两类可直接依据宿主事实完成的处理：原记录确认缺少的证据现已可用，且准则未变，可以关闭对应取证缺口；两项定义、依据、核验方案、类型和父关系完全等价时，可以证明删除重复项仍保留同一义务。这些结论分别证明取证恢复和结构保持，不宣称真实模型评价更准确，也不能用于抹掉尚未独立解释的程序失败。

schema 2 的完整语义记录按平面森林恢复；旧构建说明作为迁移历史保留，新调用使用当前协议。schema 3 同时保存层级、队列、修订范围、固定评价版本、未解决问题和验证引用。WebUI 按父子关系展示准则，并显示预算停止、待办、局部修订、未验证候选和验证结果。模拟入口支持 --owner-feedback silent --chain documents，度量信号保留在记录中但不参与改进。

验收对应关系如下；模型语义判断的实证质量与控制逻辑测试分开理解。

| 范围 | 已有证据 |
| --- | --- |
| A01 A03 A05 A06 A08 A11 A14 | test_assessor_hierarchy.py 与 test_assessor_builder.py：不等深队列、预算、越界和夹带修改、停止说明、版本冲突、中断恢复和迁移 |
| A02 A04 A09 | 关系判断写入构建及元评审协议；脚本角色案例用“费用完整但超预算”反例修正父关系，同时保留预算门控；整体判断不由子项通过推导 |

| A12 | Reviewer 测试：无独立证据保持候选，后来补充案例可以验证；合法检查器修复不抹历史失败，模型投票不能消除程序失败 |
