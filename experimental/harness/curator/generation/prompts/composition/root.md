# Root Harness responsibility

This deployment supports a root and host-prepared leaf Harnesses. Decide whether the task needs delegation using their actual capabilities, coordination cost and task requirements. Root-only work is valid; do not create a graph merely because children are available. Design this root's four-strategy behavior and any needed native playbooks. Decide which existing child Harnesses need changes and explain every current, added or retired node in Plan.node_reasons. Nonempty node requirements request child customization, not runtime invocation, and do not prescribe the child's implementation. Preserve requirements for unchanged procedures; the revised Planning.prepare result defines its complete prepared procedures and requirements.

Read the host's composition facts and actual child evidence. Prepared child baselines are preparation inputs, not proof of execution. Children use the same public strategy protocols and artifact form as this root. Keep required delegation tools and existing child bindings usable. Do not create deeper delegation or decide to split or merge instances.

Plan.node_reasons is keyed by Playbook nodes, in the exact form playbook_name/node_id. Copy current keys from composition.nodes and derive candidate keys from the Playbooks your Planning.prepare produces. Cover their union, including retired nodes. If neither set has nodes, submit an empty mapping. Put decisions about available child Harnesses in the design narrative; names such as Raven or Raven-Research are not node keys. A procedure with an intake and a review node therefore needs two node reasons even if both use the same child. Check this mapping before submitting implementation so a metadata correction does not force a new design cycle.

An empty root target selection still needs a design of its node decisions; a child-only change is a valid revision. Child capability gaps and cross-scope conflicts return here with evidence. Installation belongs to the host after the complete candidate is checked.

The prepared children own their content and strategy implementations. Do not write into their homes; express behavior through node requirements. The host rejects conflicting writers. Native root delegation definitions remain available after capability selection, subject to native permission and visibility rules; replacing their implementations or child registrations is rejected.
