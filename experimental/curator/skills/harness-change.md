# Skill：依据执行证据改造 Harness

适用于入职及后续培养。本文只讲通用方法，不针对具体任务，也不提供任何领域的答案。

## 先看证据

- 读本轮全部 `observations` 的 `reply` 与 `deliverables`，包括没被点名的成功产物；`cited` 只表示被要求引用。分数和评审意见是线索，结论要落到实际产物上。
- 执行过程在每条 observation 的 `records` 里。整条很大：用 `read_observation` 的 `path` 按下标读单条记录，或用 exec 对 `exploration.observations_file` 跑脚本按 `kind` 筛选。`provider.response` 里的 `reasoning_content` 是员工的推理，`content`、`tool_calls`、`usage` 是它的输出、工具调用和用量；`runner.event` 里 `event_type` 为 `ToolEvent` 的是工具的执行和结果；`model.input` 是员工当时看到的全部内容；`capability.*` 是每次选给员工的工具、Skill 和指引，`action.*` 是检查代码对事件的处理。任务输入在 `user`。遇到截断接着读，没读到的不算通过。
- 列明要改善的行为、必须保留的行为和对应产物。事实、诊断假设和预期效果分开写；员工的能力看执行证据，不按价格推断。
- 也看员工的工作量：每轮的模型调用和工具调用次数，重复读取同一内容，反复失败或写错的调用，调用撞到单轮上限被迫收尾。这些说明 Harness 让员工做了多余的事，或缺了一步就能用上的信息；它们拖慢工作、挤占上下文，也会损害交付。
- 每个产物只代表一次运行。只出现一次的失败是弱证据；优先处理在多个输入或多个版本里反复出现的失败，不把一次起伏归到上一次改动上。
- Analyst 的每条要求都带案例（`examples`）：`wrong` 案例写了员工做错的地方和**应该怎么处理**（`handling`），`right` 案例写了员工做对时的样子。这些案例就是改动的验收依据：改完后，同类输入都要能按"应该怎么处理"做到，做对的要继续做对。Analyst 还会说明上一轮的问题属于哪一种：员工没看到新说明、看到了没照做、照做了仍然错。这三种需要的改法不同。

## 先找出错的环节

对每个要改善的行为，取几个失败案例和做对的同类案例，沿执行记录逐步对照：

1. 员工当时看到的内容里，有没有做对所需的要求和信息；
2. 推理里有没有认出这项要求适用，理解是否与原文一致；
3. 推理或中间记录里得出的结论是否正确；
4. 正确的结论是否完整、原样地进入了动作和交付。

改法作用在第一个出错的环节：

- 缺要求或信息：补上说明，或给出读取途径。
- 理解错：讲清判断方法，用任务材料里的正反例划出边界。
- 结论错：答案能由数据按固定规则得出的操作，交给工具；需要理解的判断，拆成更小的步骤并要求写出依据。
- 结论对，但没进入交付或在传递中变了：改工作方式。这一步在固定位置完成，结论记下来，交付由记下的结论组成。内容每复述一次就可能走样，能沿用原文或已记下的结论就不重写。

再对比失败和做对的案例，找出区别条件（输入多少、出现位置、表述方式、同时在做的其他事），改法针对这个条件。同一行为可能在几个环节都出错，分别处理。定位不了就补看证据，不要直接加重改法。

## 把做对的稳定下来

员工对同一类输入时好时坏，说明它有能力做对。对比做对和做错的执行记录：做对时多看了什么、多做了哪一步、按什么顺序做。把这一步写成每次都照做的做法、清单或范例，放在员工做这件事的那一刻能看到的地方；范例只取做法和形式，不搬具体输入的内容。已经做对的行为列为必须保留，试跑后核对它们没有丢。

## 选改法

每轮最多改三个行为，优先保住红线；不顺手重写正常工作的部分。

| 顺序 | 改法 | 用途 | Raven 接口 |
|---|---|---|---|
| 0 | 案例（经验库） | 让员工看到"好的样子"：同类情况的正确处理，按情况分类 | 一个 body 交付的 Skill（`SkillContribution`），并在指引里写明员工做那个判断时先对照它 |
| 1 | System Prompt | 简短的优先级、判断方法与步骤 | `capability.strategy.select()` 的 `CapabilitySelection(guidance=...)` |
| 2 | Skill | 较长、分场景的知识与操作说明 | `_prepare_skills()` 返回 `SkillContribution`；`SkillSelection(delivery="body"/"catalog")` |
| 3 | Tool | 员工缺的能力，或能按固定规则完成的操作 | `_prepare_tools()` 返回 `ToolContribution`，实现 `raven.contracts.tool.Tool` |
| 4 | 流程 | 步骤顺序、中间记录、交付由什么组成 | `planning.strategy` |
| 5 | 检查代码 | 能按固定规则判定的条件 | `action.strategy` |

先用案例，再用说明，最后才写代码。在能作用于出错环节的办法里选最轻的。较轻的办法确实生效过（员工读到、调用、照做）仍不够，才加重；它没生效时，先改它的位置和触发方式。

## 什么时候才写代码

工具、流程和检查代码，只有同时满足下面两条才加：同一行为已经用案例和说明改过至少两轮，Analyst 的记录显示员工看到了、照做了，结果仍然错；并且你能说清这段代码解决的是哪一个出错环节。
- 每次修改新增的代码不超过 300 行。
- 新增的每个函数、类都必须在员工的执行路径上真正被调用；没被调用的删掉。
- 前几轮加的代码如果没起作用，先删掉，再考虑别的办法。
- 员工撞到单轮调用上限、超时、反复读同一份状态，说明 Harness 让它做的事太多：先删减，不要再加。

## 两类被证明有效的做法

- **兜底交付**：规定的交付物（例如定期的报告）在任何情况下都要在规定的那一轮交出去。工作没做完时，交出已完成的部分并写明缺口，不能用进度说明、计划或解释代替交付。
- **交付前核验**：交付里的每个具体事实（人数、范围、版本、原因、谁说的）都要能指到输入的原话；指不到的，改成按原话转述（"用户报告……"），或者删掉。

这两类做法适用于各种任务。它们直接对应最伤用户的两种失败：交付缺失和事实失真。

## 程序和工具的边界

- 程序只做答案能由数据按固定规则唯一确定、不需要理解含义的事，例如计算、排序、精确匹配、结构校验、在给定数据里查找。需要理解含义的判断，关键词或规则匹配既会漏也会误伤，不用程序代替。
- 同一个模型复查自己的判断，往往有同样的盲点，会放行同样的错误；没有用已知失败案例证明它能抓出错误，就不用它兜底。
- 需要程序兜底时，先做一致性检查：交付是否与员工自己记下的结论、与输入数据一致，不另立一套判断标准。条件依据输入里的结构化字段判断，不在整段文本里搜关键词。
- 适合加工具：员工缺的能力（外部数据、可靠计算、在大量数据里准确查找或整理）；现有工具难用时修工具本身。不适合：需要理解的判断；必须发生的动作（工具不会自己被调用，要保证发生，用流程或检查）；原生工具已经够用；带来的步骤和上下文多于省下的。
- 被要求的动作不给替代出口（用说明、占位或推迟代替）：弱模型会选替代出口。要么让动作更容易做，要么由流程保证它发生。

## 案例怎么写进 Harness

案例是告诉员工"好的样子"最直接的办法，可以写进 Harness，但要写成能用到新输入上的样子：
- 按"类"组织：每个案例写清它属于哪一类情况、输入长什么样（摘要原文）、正确的处理和写法、为什么（依据哪条规则）。
- 正例和反例成对给：同一类情况里做错的写法和应该的写法放在一起。
- 员工照方法处理新输入，不是照抄内容。不写成关键词清单，不写成只对某个具体输入成立的规则。
- 原输入只引能说明这类情况的短片段；不按具体输入建对照表，不搬只属于某一个输入的细节（编号、版本号、独有的原句）：新输入里不会再出现它们。
- 不搬评审或参考答案的原话；案例里的"应该怎么处理"以输入原文和交接材料为依据。

## 保持精简

- 每项改动写明针对哪个行为、预期什么变化。下次试跑后先看它是否生效：没生效，改位置和触发方式；生效了没改善，说明诊断错了，回到定位；改善了但带来新错误，就收窄。没带来预期变化的改动删除或替换，不在上面叠加。
- 优先修改或删除已有部分，再考虑新增；同一轮里每个行为最多新增一个部件。
- 改动不能让员工的工作量明显上升而没有相应收益：试跑后对比改动前后的调用次数，上升了就找出新增的步骤，删掉或合并。
- 步骤、工具和上下文越多，弱模型越容易漏做或出错；只保留有执行证据表明有用的部分。

## 怎么写

- Guidance 控制在一页内，写员工在那一刻能执行的判断步骤；“注意”“务必”一类提醒不改变行为。保留业务材料原义，不添加自己的阈值。长规范放入 Skill。
- 每个 Skill 只讲一件事，说明适用条件。常用内容用 body，其余用 catalog；保留其他仍需使用的 Skill。
- Skill 正文可从 `PreparationRequest.assets` 读取：`SkillContribution(name=..., owner="capability", package=None, files={"SKILL.md": ...}, source=...)`。通过 `SkillSelection(name=..., source="curator-capability", delivery="body")` 选中。
- 工具继承 `Tool`，提供名称、说明、参数 schema 和 `execute`；factory `create(ctx: PluginContext)` 可读取 `ctx.services.workspace`。工作目录优先使用 `raven.agent.workdir.current()`。先查实际接口契约再写实现。
- 工具说明讲清输入、输出、何时使用、结果的可靠范围。参数优先用扁平的字符串、数字和字符串列表；需要对象参数时同时接受对象和 JSON 字符串，并在报错里给出正确写法。外部服务设置超时和并发上限，保留成功的部分，明确标出失败部分；错误不能伪装为成功。
- 可恢复的工具错误使用 `ToolResult(..., retryable=False, blocks_call=False, continuation=Continuation.CONTINUE)`，由员工用已有材料继续工作；不能把恢复路径写成人工接管。

## 交付和验证

- 交付保持任务规定的形式；内部检查、记录和中间状态不得出现在交付内容里。检查不通过时，交付有依据的部分并标出不确定处，不用说明代替交付，不编造。禁止事项和权限边界照常遵守。
- 新增检查只查窄条件，标准与任务规范一致，不自行放宽或加严；不要让员工为通过你的检查额外填写复杂内容。
- 新增的工具、流程或检查，提交前用本轮已知的失败和正确案例实际跑一遍：要能处理已知失败，不误伤正确产物；做不到就不提交。
- 每个修正都可能矫枉过正：写明它可能引起的反方向错误（要求更积极，常带来误判和多余动作；要求更谨慎，常带来遗漏），试跑时专门检查。
- 试跑产物和评审交回后，先核对改动是否按预期生效，再找新问题：报错、超时、调用次数明显上升、原本做对的行为变差；有问题针对性地修，不推倒重来。
- 提交前说明：看过哪些产物和执行记录；每个行为错在哪个环节，依据是哪段推理或哪条记录；之前的改法和实际效果；改了什么、为何选该层级；删掉了哪些无效改动；失败时怎样继续交付；如何确认没有破坏原有产物、用什么证据检验效果。未经测试的效果只写作预期。
